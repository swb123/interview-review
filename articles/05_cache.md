### Q1：缓存雪崩、缓存穿透、缓存击穿分别是什么？有哪些生产级的组合解决方案？
**A：**

| 问题 | 现象 | 根因 | 危险程度 |
| --- | --- | --- | --- |
| **穿透** | 查 DB 中不存在的 key，每次都穿透缓存 | 恶意攻击或业务 bug | 单个 key 打垮 DB |
| **击穿** | 一个热点 key 过期瞬间，海量请求打到 DB | 热点 key 过期 + 高并发回源 | 仅影响热点数据 |
| **雪崩** | 大量 key 同时过期，或缓存集群宕机 | 过期时间不当或缓存故障 | 全量请求压垮 DB |


**穿透 — 三层防御**：① 参数校验 ② 布隆过滤器(误判率公式 p≈(1-e<sup>(-kn/m))</sup>k，1亿key/0.01%误判≈1.7GB) ③ 缓存空值(短TTL)。双布隆过滤器A/B交替重建策略。

**击穿 — 互斥锁 + 逻辑过期组合**：热点key推荐逻辑过期(物理永不过期+异步更新+返回旧值)，普通key用互斥锁(Double Check)。

**雪崩 — 四层防护**：① TTL随机化 ② 多级缓存熔断链(L1→L2→L3) ③ 集群高可用(自动failover) ④ 服务降级。

**组合防御矩阵**：穿透→布隆+空值+限流；击穿→逻辑过期+互斥锁+续期+降级；雪崩→TTL随机+多级+高可用+熔断。

### Q2：如何保证缓存与数据库的一致性？Cache Aside、延迟双删、订阅 Binlog 刷新各自如何实现？
**A：**

**为什么删缓存而非更新？** 并发写：B先写DB(A后写缓存)→缓存=旧值。删缓存后下次读回源最新DB→无此问题。

**Cache Aside**：读(cache miss→读DB→写缓存)、写(更新DB→删缓存)。并发竞态：读miss+读旧DB→写更新DB+删缓存→读把旧值写回缓存(概率极低但可能)。

**延迟双删**：①删缓存→②更新DB→③sleep(200~500ms)→④再删缓存。延迟需大于"读DB+写缓存"的耗时。

**Binlog 异步（生产推荐）**：MySQL→Canal→RocketMQ→缓存更新Consumer(100ms~1s延迟)。优点：零侵入、MQ重试、准实时。

**一致性能彻底解决吗？** 不能。五层保障：Cache Aside(<100ms)→Binlog补偿(100ms~1s)→短TTL兜底(<TTL)→对账(T+1)→强制读主库(0延迟)。核心洞察：不同业务对一致性要求不同。

### Q3：Redis 实现分布式锁有哪些关键点？从单实例到 Redlock 的演进及安全边界是什么？
**A：**

**进化史**：V1(SETNX+EXPIRE两步非原子→死锁)→V2(SET NX PX原子)→V3(Lua释放防误删)→V4(Redisson Watchdog每10s续期)→V5(Redlock多节点多数派)。

**Watchdog**：加锁SET lockKey uuid:threadId NX PX 30000→Netty TimerTask每10s续期到30s(Lua判断value一致才续)→宕机自然过期。

**主从锁丢失**：主节点SET成功→未同步到从→主宕机→从提升为新主→新Client也SET成功→互斥被打破。根因：Redis主从复制是异步的。

**Redlock**：向N个独立节点依次SET→多数派成功+总耗时<TTL→加锁成功。争议：Martin Kleppmann认为时钟跳变/GC可打破互斥→资金类用ZK/etcd+Fencing Token；非资金秒杀够用。

### Q4：什么是热点 Key？如何探测和解决热点 Key 问题？多级缓存架构如何设计？
**A：**

**量化**：单Redis分片~5-10万QPS，一个爆款50万QPS→单分片瓶颈。

**探测方案对比**：客户端SDK统计(精准需自研)、代理层统计(透明)、Redis --hotkeys(4.0+非实时)、JD HotKey(京东开源实时)、网络抓包+Flink(无侵入复杂)。

**解决方案矩阵**：QPS<5000无特殊→5000~50000从节点+本地缓存→>50000拆分+多级组合。

**多级缓存架构**：L1 Caffeine(1000key/1~5s TTL/极热点)→L2 Redis Cluster(TB级/全量热数据)→L3 MySQL(限流保护)。L1<堆内存10%、L2按热点比例20%估算。failover：L2不可用→L1兜底→Sentinel限流→DB。

**自动热点流水线**：SDK统计QPS→上报HotKey集群→聚合判断→推送热点列表→Client写入Caffeine→Pub/Sub主动失效。

### Q5：如何设计一个高可用的缓存系统？（开放式架构题）
**A：**

**容量规划公式**：分片数=目标QPS/单实例×2；内存=(用户×条目×大小)×1.5碎片。例：50万QPS/10TB→16主分片(每片625GB)+1主2从=32~48实例。

**选型决策**：Cluster(无中心+在线扩容)、Lettuce+连接池(非阻塞+拓扑感知)、Protostuff序列化、AOF everysec+混合持久化、allkeys-lru、大Key拆分压缩。

**高可用矩阵**：单从宕→自动failover；主宕→选举(秒级，分片不可写)；半数主宕→FAIL全停；缓存全挂→L1兜底+限流→降级数据；网络分区→少数拒绝服务。

**降级链路**：正常→L2故障→L1旧数据兜底→L1也miss→DB限流查询→静态降级→503。

**监控指标**：命中率<90%、p99>10ms、内存>80%、连接>80%maxclients、主从延迟>1s、分片QPS>80%。

**Redis 内存管理**：

内存碎片率 = used_memory_rss / used_memory（>1.5需关注）。碎片原因：jemalloc频繁增删key。解决：activedefrag yes(4.0+)、MEMORY PURGE、重启恢复。

大Key标准：String>10KB、集合>5000元素。扫描：redis-cli --bigkeys/--memkeys、memory usage key。拆分方案：大String压缩、大Hash分片、大List按时间分、大Set按hash分。

淘汰策略选择：allkeys-lru(通用缓存首选)、allkeys-lfu(冷热分明更精确)、volatile-lru(有永久数据)、volatile-ttl(先淘汰即过期)、noeviction(拒绝淘汰)。调优：maxmemory-samples 10、MEMORY DOCTOR诊断。

### Q6：Redis 的 BitMap、HyperLogLog、GEO 以及 Lua 脚本分别有哪些典型的业务应用？
**A：**

**BitMap**：用户签到(SETBIT一年365bit≈46B)、在线状态(1亿用户≈12MB)、布隆过滤器(多hash+SETBIT/GETBIT)、画像标签(BITOP AND/OR交集)。

**HyperLogLog**：UV统计(PFADD/PFCOUNT，12KB统计2^64元素误差0.81%)、去重合并(PFMERGE)。限制：不能获取具体元素。

**GEO**：底层Sorted Set+GeoHash(二分编码经纬度52位)。附近的人(GEORADIUS)、门店距离(GEODIST)、配送范围。

**Lua脚本**：单线程原子性(非事务原子性，不支持回滚)。注意事项：超时5s(SCRIPT KILL)、缓存SHA(EVALSHA)、集群key同slot、禁随机函数、复杂度O(n)且n<100。Lua vs MULTI/EXEC：支持条件判断+循环、1次RTT。

### Q7：缓存预热、缓存更新、缓存降级分别是什么？如何实现平滑上下线？
**A：**

**预热三策略**：全量(启动批量SET→Redis)、增量(RDB恢复+Binlog追平)、按需(灰度放量利用miss自动预热)。

预热流程：启动不注册→预热脚本→标记完成→注册Nacos→10%→50%→100%。

**更新对比**：过期懒加载(通用)、主动更新(强一致)、Binlog订阅(100ms~1s解耦)、定时全量(字典)。

**降级五级**：正常Redis→本地缓存旧数据→DB限流→硬编码兜底→503。

**平滑上下线**：上线(旧实例摘除等drain→新实例预热→灰度注册)；下线(权重设0→grace period 30s→释放连接池→关闭)。

### Q8：在高并发下，如何设计一个"库存扣减"的缓存方案？
**A：**

**核心链路**：网关Sentinel限流→Hash(uid)路由Redis槽位→Lua原子扣减→MQ异步落库→对账。

**库存槽位(Slotting)**：单key DECR极限约10万QPS，50万需≥5槽位。库存10000→stock:sku_0~9各1000，请求user_id%10随机选槽→定时MGET汇总。

**防超卖五层**：Redis Lua原子性→Hashtag同分片→DB唯一索引→unsigned字段→对账。

**主从切换超卖**：主节点DECR stock=4→宕机未同步→从提升stock=5→又卖5个→超卖。对策：库存只走主节点、AOF everysec、哨兵min-slaves-to-write 1+min-slaves-max-lag 10。

**完整链路**：前端按钮置灰+验证码→CDN→网关Sentinel→Redis Lua槽位→MQ削峰→DB订单→对账→纯DB降级兜底。

### Q9（新增 — Redis 集群）：Redis Cluster 的原理是怎样的？
**A：**

**Cluster vs 哨兵**：Cluster内置Gossip去中心化、16384 slot分片、在线reshard、smart client MOVED/ASK重定向、TB级适用(哨兵<10GB)。

**数据分片**：CRC16(key)%16384→slot→路由到持有节点。Hash Tag `{user}:1001`确保相关key同分片。

**Reshard**：标记MIGRATING/IMPORTING→逐个MIGRATE→Gossip传播→客户端MOVED更新路由。迁移中：ASK(一次性) vs MOVED(永久重定向)。

**Failover**：PING/PONG→PFAIL→投票→FAIL→从节点选举→新主Gossip广播。时间≈15~30s。

**Cluster限制**：不支持跨slot多key、不支持跨slot事务、Lua key必须同slot、主从复制异步(不保证强一致)。

### Q10（新增 — 大促缓存实战）：备战双11，如何设计一个支撑百万 QPS 的缓存架构？
**A：**

**容量规划**：5000万DAU、100万QPS、500热点商品占80%流量。热点80万→本地缓存90%命中吸收72万→Redis扛8万。缓存2GB热数据+20TB Feed。

**架构全景**：CDN/WAF→Gateway(Sentinel限流)→热门(L1 Caffeine 1s TTL→L2 Redis热点分片)/普通(L2 Cluster 16主+16从→L3 TiDB)。

**大促备战清单**：前1月全链路压测→前1周缓存预热+热点预判→前1天扩容+reshard→活动监控→异常自动降级。

**故障演练**：单分片宕(kill→30s恢复)、全集群宕(自动→本地缓存+DB限流)、热点10倍(自动探测→本地缓存<5s)、穿透攻击(布隆→空值→限流实时)。

**成本分析**：Redis Cluster 16分片~3万/月(50万QPS)、加本地缓存+0元(+30万QPS)。本地缓存2MB内存换30万QPS——ROI极高。

### Q11（新增 — 主从复制）：Redis 主从复制是怎么实现的？全量复制、增量复制、命令传播的原理各是什么？
**A：**

**为什么需要主从**：解决单点故障——宕机恢复期无法服务、硬盘故障数据全丢。主从模式 = 多服务器数据一致 + 读写分离（主写从读，写命令自动同步给从）。

**第一次同步（全量复制）三阶段**：

**① 建立链接、协商同步：**从执行 `replicaof <ip> <port>`（5.0 前 slaveof）→ 从发 `psync runID offset`（首次 runID=?、offset=-1）→ 主回 `FULLRESYNC runID offset`，决定走全量复制。

**② 主同步数据给从：**主执行 `bgsave` 生成 RDB（子进程异步，不阻塞主线程）发给从 → 从清空旧数据、载入 RDB。

**③ 主发送新写命令：**生成 RDB、传输 RDB、从加载 RDB 三个时间间隙的写命令，主写入 `replication buffer`；从载入完成回复确认 → 主把 buffer 里的命令发给从 → 数据一致。

**命令传播（长连接）**：首次同步后维持 TCP 长连接，主持续把写命令传播给从（避免频繁建连的开销）。

**级联架构分摊压力**：从也可以有自己的从（“经理”角色）——多个从都与主全量同步时，主会忙于 fork()（内存大时 fork 阻塞主线程）且传输 RDB 占满带宽；级联把 RDB 生成/传输压力下放。

**增量复制（2.8+）**：断线重连不再全量。从重连发 `psync`（offset 非 -1）→ 主回 `CONTINUE` → 只发断线期间的写命令。

**• repl_backlog_buffer**：环形缓冲区（默认 1M），主传播命令时同时写入，满了覆盖旧数据。主 master_repl_offset 记“写到哪”、从 slave_repl_offset 记“读到哪”；从要读的数据还在 backlog 里 → 增量，已被覆盖 → 退回全量。

**• 调优：**`repl-backlog-size` ≥ 断线平均秒 × 每秒写命令量，建议再 ×2。例：1MB/s × 5s = 5MB → 配 10MB。

**高频追问**：

| 问题 | 答案 |
| --- | --- |
| 主从是长连接还是短连接？ | 长连接。 |
| 怎么判断节点是否正常？ | ping-pong 心跳：主每 10s ping 从（repl-ping-slave-period）；从每 1s 发 replconf ack{offset}（监测网络 + 上报偏移量检查丢数据）。 |
| 过期 key 如何同步？ | 主淘汰 key 后模拟一条 del 命令发给从，从执行删除。 |
| 同步复制还是异步复制？ | 异步：主写完本地缓冲区即返回客户端，异步发给从（未同步数据可能丢失）。 |
| replication buffer 和 repl_backlog_buffer 区别？ | backlog：增量复制阶段、全局一个、环形满了覆盖旧数据；replication buffer：全量/增量都有、每个从独立一个、满了断开连接重连 → 重新全量。 |
| 主从数据不一致怎么应对？ | ① 主从避免跨机房；② 监控 INFO replication 的 master_repl_offset − slave_repl_offset 差值，超阈值摘除该从节点（阈值设大防无节点可读）。 |
| 主从切换如何减少数据丢失？ | 两类丢失：异步复制丢失（主写完未同步即宕机）、脑裂丢失（旧主失联仍收客户端写 → 哨兵选新主 → 网络恢复旧主降级清空数据 → 丢失）。对策：min-slaves-to-write N + min-slaves-max-lag T —— 从节点数小于 N 或 ACK 延迟超过 T 秒，主拒绝写。例：N=1、T=12s、哨兵 down-after=10s，主卡 15s → 客观下线切主且旧主已限写 → 零丢失。 |
| 主挂了如何自动切换？ | 从不能自动升级为主（需人工），靠哨兵机制自动完成故障发现 + 故障转移 + 通知应用方。 |


### Q12（新增 — 底层数据结构）：Redis 的 String、Hash、ZSet 底层分别用什么数据结构实现？跳表、压缩列表的原理？哈希表如何渐进式扩容？
**A：**

**SDS（简单动态字符串）**：String 用 SDS 而非 C 字符串——① O(1) 获取长度（len 字段）② 二进制安全（不依赖 \0 结尾，可存图片等二进制）③ 杜绝缓冲区溢出（拼接前检查容量）④ 空间预分配 + 惰性释放，减少内存重分配次数。String 三种编码：int（整数值）、embstr（短字符串一次分配）、raw（长字符串）。

**哈希表与渐进式 rehash**：Hash 底层是哈希表，负载因子过大触发扩容（或缩容）。rehash 用两个哈希表 ht[0]/ht[1]：**渐进式 rehash** 不一次性搬完，每次增删改查顺带把一部分桶搬到新表（分摊单次请求延迟，避免大表迁移长时间阻塞）；查询时先查 ht[0] 再查 ht[1]；搬完后交换指针释放旧表。

**跳表（ZSet 大数据量的底层）**：多层有序链表，每层是下一层的抽样——创建节点时生成随机数，小于 0.25 就升一层，层高上限 32。查找从顶层往下跳，平均复杂度 O(logN)。**为什么不用 B+ 树**：跳表实现简单（无旋转/分裂的平衡操作）、并发友好（可逐节点加锁）、内存利用更紧凑；B+ 树的优势是减少磁盘 IO，而 Redis 数据全在内存中，用不上。

**压缩列表（ziplist）与连锁更新**：连续内存块的紧凑结构，小数据量时省内存。缺点：某个 entry 长度变化可能触发**连锁更新**——其后所有 entry 的 prevlen 字段级联变长重写，造成性能退化。**listpack**（Redis 7.0+ 替代 ziplist）：改为记录每个 entry 自身长度（不记 prevlen），彻底消除连锁更新；quicklist 是 ziplist/listpack 与双向链表的混合体。

**高频追问**：

| 问题 | 答案 |
| --- | --- |
| set 和 zset 区别？ | set 无序去重（整数集/哈希表）；zset 按 score 排序（小数据 ziplist、大数据跳表），支持排名/范围查询 |
| ZSet 在项目里怎么用？ | 排行榜（score 分数 + 排名 + 范围）、延迟队列（时间戳做 score）、滑动窗口限流 |
| 哈希表扩容时读请求怎么查？ | 渐进式 rehash 期间先查 ht[0]，未命中再查 ht[1]，搬完切换 |
| quicklist 解决什么问题？ | 链表节点太多指针浪费内存、ziplist 太大连锁更新风险高——quicklist 把两者组合，按节点大小控制平衡 |

### Q13（新增 — 线程模型）：Redis 为什么这么快？IO 多路复用和 Reactor 网络模型是怎么回事？6.0 之后哪些地方用了多线程？
**A：**

**为什么快**：① 纯内存操作 ② 单线程串行执行命令——没有锁竞争、上下文切换 ③ IO 多路复用（epoll）一个线程管理海量连接 ④ 高效数据结构（SDS/跳表/压缩列表）与事件驱动框架。

**IO 多路复用**：一个线程同时监听多个 socket 的事件（epoll 在内核维护就绪队列），连接有事件才处理，避免「一连接一线程」的阻塞模型。核心：单线程 + 事件循环 + 就绪事件队列。

**网络模型演进（Reactor）**：6.0 之前是单 Reactor 单线程——连接建立、命令解析、命令执行、响应写回全在一个线程。6.0 之后引入 IO 多线程（默认关闭）：主线程负责连接与命令执行，IO 线程组负责 socket 数据读写。**关键**：命令执行仍是单线程串行（保证原子性），多线程只用于网络 IO。开启：io-threads 4（N-1 个 IO 线程）+ io-threads-do-reads yes。

**原子性**：单条命令天然原子（单线程执行）；多条命令靠 Lua 脚本（整个脚本执行期间不被打断）或 MULTI/EXEC 事务（命令入队期间不被穿插，执行时单线程串行）。

**高频追问**：

| 问题 | 答案 |
| --- | --- |
| Redis 支持并发操作吗？ | 命令执行单线程串行，天然线程安全；多线程只用于网络 IO 读写 |
| 单线程为什么能扛高并发？ | IO 多路复用让一个线程同时处理上万连接的读写事件，瓶颈在内存/CPU 而非连接数 |
| Redis 主从是 AP 还是 CP？ | AP——网络分区时保证可用性，牺牲强一致（主从异步复制可能丢数据） |
