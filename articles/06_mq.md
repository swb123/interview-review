### Q1：队列模型 vs 发布/订阅？RocketMQ 和 Kafka 如何实现？
**A：**

| 模型 | 消费方式 | 典型实现 | 场景 |
| --- | --- | --- | --- |
| **队列（点对点）** | 一条消息只被一个消费者消费一次 | RabbitMQ Queue | 任务分发、负载均衡 |
| **发布/订阅** | 一条消息被所有订阅者消费 | Kafka Topic+独立ConsumerGroup | 广播通知、实时同步 |


**RocketMQ/Kafka 的"混合模型"**：通过 **ConsumerGroup** 实现。同 ConsumerGroup 内的消费者竞争消费（队列模型）、不同 ConsumerGroup 间独立消费全部消息（发布/订阅）。

### Q2：如何保证消息不丢失？从生产、Broker、消费三环节分析。
**A：**

| 环节 | 丢失场景 | 解决方案 |
| --- | --- | --- |
| **生产者** | 网络超时，send未收到确认 | `retryTimes=3` + 仅对幂等操作重试 |
| **生产者** | 异步发送，本地buffer满丢弃 | 同步/异步+回调check + 降级写本地日志 |
| **Broker** | 异步刷盘，宕机丢数据 | RocketMQ: `flushDiskType=SYNC_FLUSH`; Kafka: `log.flush.interval.messages=1` |
| **Broker** | 主从异步复制，主宕机丢数据 | RocketMQ: SYNC_MASTER; Kafka: `acks=all + min.insync.replicas>=2` |
| **消费者** | 自动提交offset，消费失败未重试 | **手动提交** + `consumeMessageOrderly` / `enable.auto.commit=false` |


**Kafka "acks=all" 完整方案**：

```plain
acks=all                        ← 所有ISR副本确认后才返回
min.insync.replicas=2           ← 最少2个ISR, 否则拒绝写入
replication.factor=3            ← 3副本
unclean.leader.election.enable=false ← 禁止落后副本选主
```

### Q3：顺序消息如何实现？全局有序 vs 分区有序？
**A：**

**核心原则**: 同一业务标识的消息发送到同一队列/分区。

| 方式 | 实现 | 原理 | 吞吐量 |
| --- | --- | --- | --- |
| **RocketMQ 分区有序** | `MessageQueueSelector` 按业务key选择同一Queue | 同一Queue的消息Consumer单线程串行消费 | 高（并发数=Queue数） |
| **RocketMQ 全局有序** | 所有消息发送到同一个Queue | 单Queue→单Consumer→串行 | 极低 |
| **Kafka 分区有序** | producer指定key→同一partition | 同一partition内有序 | 高 |
| **Kafka 全局有序** | 单partition Topic | 全局限流严重 | 极低 |


**消费端如何保证顺序？** RocketMQ 对同一 MessageQueue 的消息加**本地ReentrantLock**，确保同一时刻只有一个线程消费该队列。回滚/重试时不跳过，阻塞等待重试成功。

### Q4：幂等性如何设计？
**A：**

```plain
幂等三策略:
① 全局唯一MsgID: RocketMQ自动生成，consumer做去重check（Redis SETNX msgId:xxx）
   问题: 重试消息的MsgID会变 → 需要业务唯一键

② 业务唯一键: 如订单号，consumer端做唯一索引/Redis去重
   UPDATE订单 WHERE order_no=? AND status=待处理 → affected rows=1才处理

③ Redis去重表: SET msgKey TTL(N天) NX → 成功才消费
   注意TTL: 大促期间可能redis内存压力，需按消息类型设定合理TTL
```

| 策略 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| DB唯一索引 | 强一致 | 影响DB性能 | 资金类 |
| Redis去重 | 🏆 高性能 | TTL后可能重复 | 大部分业务 |
| 业务状态机 | 天然幂等 | 需设计状态流转 | 状态变更类 |

### Q5：消息积压如何处理？短期止血/长期预防/消费者保护？
**A：**

```plain
短期止血（1分钟内）:
① 临时扩容消费者实例（最多=partition/queue数）
② 紧急降级消费逻辑（跳过非核心业务，如风控校验/日志）
③ 先消费不处理（只记offset，把积压快速消化，事后补偿）

长期预防:
① 消费者处理能力 = partition数 × 单partition消费速率
② 生产者速率 < 消费者处理能力（监控+告警）
③ 独立死信队列+重试机制

消费者流控:
RocketMQ: DefaultMQPushConsumer.setPullBatchSize(小值) + 背压
Kafka: max.poll.records=小值 + 处理完再poll
```

**监控指标**：`lag(未消费消息数) > 10万告警`、`消费RT p99 > 500ms告警`、`死信队列条数 > 0告警`。

### Q6：RocketMQ 事务消息原理？与 Kafka 事务有何不同？
**A：**

**RocketMQ 事务消息流程**：

```plain
① Producer向Broker发送半消息（Half Message，消费者不可见）
② Producer执行本地事务
③ (a)成功→Commit半消息→消费者可见
   (b)失败→Rollback半消息→Broker删除
④ Broker未收到确认→定时回查Producer→根据CheckListener结果决定Commit/Rollback
```

**Kafka 事务（EOS）**：

```plain
① 生产者: enable.idempotence=true + transactional.id
② beginTransaction() → send() → sendOffsetsToTransaction() → commitTransaction()
③ 消费者: isolation.level=read_committed（过滤未提交的事务消息）
④ 跨分区原子写入: 多个partition的消息要么全成功要么全失败
```

**核心差异**：

| 维度 | RocketMQ 事务消息 | Kafka EOS |
| --- | --- | --- |
| 目标 | 分布式事务最终一致 | 生产者幂等+跨分区原子 |
| 消费者侧 | 无特殊处理 | 需过滤未提交消息 |
| 复杂度 | 低（仅Producer+Broker配合） | 中（需事务协调器TransactionCoordinator） |
| 场景 | 下单+扣库存最终一致 | 流计算exactly-once |

### Q7：Kafka 高吞吐的设计原理？
**A：**

| 优化技术 | 原理 | 效果 |
| --- | --- | --- |
| **零拷贝（sendfile）** | 磁盘→OS缓冲区→Socket DMA直传，跳过用户态 | 减少2次CPU拷贝+2次上下文切换 |
| **顺序写入** | partition内消息追加写，非随机IO | 磁盘顺序写速度 ≈ 600MB/s，接近内存 |
| **PageCache** | 利用OS页缓存，热数据命中内存 | 读免IO |
| **批量压缩** | 消息批量压缩发送（gzip/snappy/lz4） | 带宽降 70%+ |
| **分区并发** | 多partition并行读写 | TPS ≈ partition数 × 单partition TPS |
| **稀疏索引** | offset→position 的稀疏索引，二分查找 | 内存占用极小 |


**零拷贝 sendfile vs mmap**：

| 方式 | 使用方 | 适用场景 | 原理 |
| --- | --- | --- | --- |
| **sendfile** | Kafka | 数据从磁盘→网络，Producer→Consumer直传 | 内核态DMA直传，零CPU拷贝 |
| **mmap** | RocketMQ | 磁盘文件映射到用户态内存 | 直接在内存中读写，操作系统自动回写磁盘 |

### Q8：RocketMQ 的存储结构是怎样的？
**A：**

```plain
CommitLog + ConsumeQueue 双层存储:

CommitLog（所有Topic共享):
  [消息1(TopicA)] [消息2(TopicB)] [消息3(TopicA)] ...  ← 顺序追加写

ConsumeQueue（按Topic+Queue组织):
  TopicA/Queue0: [offset1,size1] [offset3,size3]  ← 只是引用！
  每条 ConsumeQueue 条目: {CommitLog offset, size, tag hashcode}
  仅 20 字节 → 内存占用极小

消费: Consumer → 查ConsumeQueue → 获取CommitLog位置 → 批量mmap读取
```

**为什么性能也高？** CommitLog 顺序追加写（单文件+锁）→ 磁盘顺序IO；ConsumeQueue 是纯索引，内存占用极低；mmap 将 CommitLog 映射到进程地址空间，读近似直接内存访问。

### Q9（场景题）：设计"订单超时自动取消"，用 MQ 实现延迟消息。
**A：**

| 方案 | 实现 | 适用场景 |
| --- | --- | --- |
| **RocketMQ 延迟消息** | `message.setDelayTimeLevel(3)` 预设18个级别（1s→2h） | 🏆 延迟级别匹配时推荐 |
| **RocketMQ 定时消息（5.x）** | 任意时间点投递 | 精确到秒的延迟 |
| **Kafka 变通方案** | 发送到临时Topic → 定时任务消费 → 到期后投递到真实Topic | 灵活但需自建调度 |
| **纯 Redis + 定时任务** | ZSet存储(score=过期时间) → 每秒扫score<now的 | 轻量级但可靠性一般 |


**RocketMQ 延迟消息原理**：延迟消息先写入 `SCHEDULE_TOPIC_XXXX`，每个延迟级别一个ConsumeQueue；Broker定期扫描到期消息→重新投递到原始Topic。

### Q10：为什么要用消息队列？引入代价是什么？

### Q12：消息回溯/重放怎么做？
**A：**

+ RocketMQ: `DefaultMQAdminExt.resetOffsetByTimestamp(time)` — 按时间点重置消费位点
+ Kafka: `kafka-consumer-groups --reset-offsets --to-datetime "2024-01-01T00:00:00" --execute`

### Q13：Rebalance 是什么？触发条件与危害？
**A：**

**触发条件**：消费者上下线、宕机心跳超时、新 partition/queue 加入、Topic 扩容。

**危害**：Rebalance 期间该 ConsumerGroup **STW 停止消费** → 消息积压；重新分配 partition 后可能重复消费。

**优化**：RocketMQ 客户端队列负载算法（`AllocateMessageQueueAveragely` 平均分配）；Kafka `session.timeout.ms` 调大避免误判；Consumer 优雅下线（发送 LEAVE_GROUP 再关闭）。

### Q17（新增 — RabbitMQ 与高频追问）：RabbitMQ 的四种交换机类型是什么？与 AMQP 的关系？延迟队列和死信机制怎么实现？
**A：**

**AMQP 与 RabbitMQ**：AMQP（Advanced Message Queuing Protocol，高级消息队列协议）是消息中间件的开放协议标准，RabbitMQ 是它的典型实现。RabbitMQ 的模型：生产者发消息到 **Exchange（交换机）**，交换机按 **Binding（绑定规则）** 路由到 **Queue**，消费者从队列取消息。

**四种交换机**：

+ **direct**：按 routing key 精确匹配（默认交换机即 direct，队列名作 routing key）
+ **fanout**：广播到所有绑定队列，忽略 routing key
+ **topic**：按通配符匹配 routing key（* 匹配一个词，# 匹配零个或多个词）
+ **headers**：按消息头属性匹配，很少用

**延迟队列实现**：RabbitMQ 没有原生延迟队列——用 **TTL + 死信交换机（DLX）** 组合：消息设置 TTL（或队列 TTL），过期后自动转发到死信交换机 → 路由到延迟队列被消费。**死信三种来源**：① 消息被拒绝/否定确认且不重回队列（requeue=false）② TTL 过期 ③ 队列长度满溢出（x-max-length）。

**可靠性保障**：生产者 confirm 确认机制 + 消息/队列/交换机全部持久化（durable）+ 消费者手动 ACK + 失败重试与死信兜底。

**高频追问（Kafka）**：

| 问题 | 答案 |
| --- | --- |
| Kafka 为什么一个分区只能被组内一个消费者消费？ | 保证同一分区消息只被组内一个实例消费，天然有序且不会重复分配——一个分区对应一个消费线程 |
| 分区数和消费线程数什么关系？ | 消费线程数大于分区数时多余线程空闲：一个分区最多被一个线程消费，扩容消费者前先增分区 |
| 消息队列参考了哪种设计模式？ | 观察者模式/发布订阅模式：消费者注册订阅，消息到达时通知所有订阅者 |
