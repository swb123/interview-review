### Q0.5（新增 — 概念辨析）：什么是分布式系统？分布式与微服务有什么区别？
**A：**

**什么是分布式系统**：多台独立机器通过网络协同工作，对外表现得像一台机器。关键在「协同」——节点之间如何通信、如何分工、如何保证数据一致，这是所有分布式难题的根源。

**为什么需要分布式**：① 单机性能/容量天花板（CPU、内存、磁盘、带宽有物理上限）② 可用性要求（单点故障不可接受）③ 业务地理分布（跨机房/跨地域部署）。

**分布式 vs 微服务（核心区别）**：

+ **分布式是「物理部署方式」**——解决单机扛不住的问题，关注点是把工作分摊到多台机器上；
+ **微服务是「软件架构设计思想」**——解决单体应用难维护/难协作/难独立演进的问题，关注点是把系统拆成按业务边界划分的独立服务。
+ **两者正交**：可以是分布式但不是微服务（单体应用多副本负载均衡，也是分布式部署）；也可以是微服务但暂时单机部署（开发环境）；生产环境常见是两者结合（微服务架构 + 每个服务多实例分布式部署）。

**分布式引入的核心挑战**：网络不可靠（丢包/延迟/分区）、节点故障（宕机/GC停顿）、时钟不同步（不能用本地时间做全局决策）——这正是 CAP、BASE、一致性算法（Raft/Paxos）要解决的问题。

### Q1：CAP 理论是什么？在分布式系统中如何理解"三选二"？结合 BASE 理论谈谈互联网系统的取舍。
**A：**

**1. CAP 定义**

+ **一致性（Consistency）**：所有节点在同一时间看到的数据完全一致（更准确的说法是**线性一致性 / Linearizability**）。
+ **可用性（Availability）**：每个非故障节点都能在正常响应时间内返回非错误响应（不一定是最新数据）。
+ **分区容错性（Partition Tolerance）**：系统在发生网络分区（节点间无法通信）时仍能继续运行。

**2. 深入理解：CAP 不是"三选二"，而是"P 必选 + CA 权衡"**

+ 网络分区是分布式系统的**客观存在**——网线会断、交换机会坏、机房会断电，所以 **P 是无法逃避的**。
+ 真正的问题是：**当分区发生时，你选 C 还是 A？**
+ 当没有分区时（系统正常运行时），C 和 A 都可以同时满足。所以 CAP 更准确的理解是：**发生分区时，系统只能在 C 和 A 之间做取舍**。

**3. CAP 是谱系，不是二分法**

+ 没有哪个系统是"100% CP"或"100% AP"，实际系统位于 C-A 轴上的某个位置。
+ 例如 ZooKeeper：正常时可用性很高（毫秒级响应），分区时倾向于 CP（拒绝少数派服务），但并不是"完全不可用"。

**4. PACELC 扩展 — P7 加分项**

+ **P（分区）→ A（可用性）或 C（一致性）**
+ **E（无分区）→ L（低延迟）或 C（一致性）**
+ 这意味着：即使在正常运行状态下，系统也需要在**延迟**和**一致性**之间选择。
+ 举例：
    - ZooKeeper：PACELC → **PC/EC**（分区选 C，正常也选 C）
    - Cassandra：PACELC → **PA/EL**（分区选 A，正常选低延迟）
    - MongoDB（默认写关注）：PACELC → **PA/EC**（分区保可用，正常保一致）

**5. BASE 理论**

+ **BA（Basically Available）**：基本可用——系统出现故障时允许损失部分可用性（如响应变慢、功能降级），但核心功能仍可用。
+ **S（Soft State）**：软状态——系统中的数据允许存在中间状态，不要求数据时刻一致。
+ **E（Eventual Consistency）**：最终一致性——不保证数据实时一致，但保证在一定时间窗口后，所有副本最终达到一致。
+ BASE 不是"放弃 C"，而是**用最终一致替换强一致**，配合补偿、对账、重试来满足业务需求。

**6. 业务链路推演法（P7 必杀技）**

以「用户下单 → 扣库存 → 生成订单 → 扣款 → 发消息」为例，逐环节分析：

| 环节 | 选型 | 一致性要求 | 可用性要求 | 理由 |
| --- | --- | --- | --- | --- |
| 创建订单 | AP + 最终一致 | 允许短暂不一致 | 极高，不能丢单 | 订单创建后异步写入，前端立即返回 |
| 扣库存 | CP（Seata AT / TCC） | 强一致，不能超卖 | 高 | 库存是稀缺资源，超卖不可接受 |
| 扣款 | CP（TCC，有对账兜底） | 强一致 | 高 | 涉及资金，必须强一致 + 对账 |
| 发消息 | AP + 最终一致 | 最终一致，允许延迟 | 高 | 用 MQ 异步，失败可重试 |


> **P7 亮点**：不是笼统地说"我们系统选 AP"，而是能在一条完整的业务链路中，逐环节说清楚 C 和 A 的取舍，并给出兜底方案。

### Q1.5（补全 — 一致性模型）：分布式系统中的一致性模型有哪些？
一致性模型定义了"系统看起来如何执行操作"的约定，强度从强到弱：

| 模型 | 定义 | 示例 | 代价 |
| --- | --- | --- | --- |
| **线性一致性** | 所有操作看起来在某个全局时间点原子执行，操作顺序与真实时间一致 | etcd(线性读) | 最强，延迟最高 |
| **顺序一致性** | 所有操作按全局顺序执行，但不保证与真实时间一致 | ZK(默认读) | 较强 |
| **因果一致性** | 有因果关系的操作保证顺序，无关操作可任意顺序 | COPS数据库 | 中等 |
| **最终一致性** | 无新写入后，所有副本最终一致 | DNS、Cassandra | 最弱，延迟最低 |


关键场景区分：线程A set(x,1)、线程B set(x,2)、线程C get(x)=2 then get(x)=1→线性一致性不允许(时间逆序)，顺序一致性允许(只要所有进程看到的顺序一致即可)。

> P7面试：根据业务需求选择一致性级别。资金扣减→线性一致；微博Feed→因果一致；DNS→最终一致。

### Q2：Paxos 和 Raft 是解决什么问题的？Raft 的核心流程是怎样的？为什么比 Paxos 更易实现？
**A：**

**1. 解决的问题**  
分布式一致性问题——如何在一个可能发生节点故障、网络延迟的集群中，让多个节点对某个值（日志序列）达成一致，实现一个**可靠的复制状态机（Replicated State Machine）**。

**2. Raft 核心流程**

**2.1 Leader 选举**

+ 三种角色：**Leader**（处理所有写请求）、**Follower**（被动复制）、**Candidate**（选举中的临时状态）。
+ 选举超时（150ms~300ms 随机）触发：Follower 收不到心跳 → 转为 Candidate → Term+1 → 给自己投票 → 广播 `RequestVote` RPC。
+ 获得**半数以上**选票当选。每个 Term 最多一个 Leader。
+ 平票 → 超时后新一轮，**随机化超时**是减少冲突的关键设计。

**2.2 日志复制**

+ 所有写请求走 Leader → 追加本地日志 → 并行 `AppendEntries` 到 Follower。
+ **半数以上**确认持久化后 → 日志"已提交" → 应用到状态机 → 返回客户端。
+ 后续心跳携带 `leaderCommit`，Follower 随之提交。

**2.3 安全性保证**

+ **选举约束**：Candidate 的日志必须至少和大多数节点一样新（lastLogTerm 大者胜；term 相同则 lastLogIndex 大者胜），确保当选者拥有所有已提交日志。
+ **Leader Completeness**：Leader 永远不覆盖或删除本地已提交的日志。**Raft 不直接提交之前 Term 的日志**——它只提交当前 Term 的日志，但提交当前 Term 的日志时会**隐式**让之前 Term 的已复制到多数派的日志也变成"已提交"。这个设计避免了前任 Leader 的日志被错误回滚。

**3. Raft 进阶话题（P7 分水岭）**

**3.1 日志压缩（Snapshot / Log Compaction）**

+ 日志会无限增长，必须压缩。
+ Leader 拍快照（Snapshot）→ 包含当前状态机的完整状态 + 最后包含的日志 index+term。
+ Follower 落后太多时，Leader 发送 `InstallSnapshot` RPC 而不是逐条追日志。
+ **工程要点**：快照频率、快照期间的写阻塞、大快照的分块传输。

**3.2 成员变更（Membership Change / Joint Consensus）**

+ 不能一步切换到新配置（如从 3 节点扩到 5 节点）——这会导致两个不相交的多数派同时存在，产生双 Leader。
+ Raft 方案：**Joint Consensus（联合共识）**——先进入过渡配置 C_{old,new}，它同时包含新旧两套节点，这个阶段的决策需要两套多数派都同意 → 确认后再切换到 C_{new}。
+ **一次只变更一个节点**（Single-Server Change）是更简单的工程实现方案。

**3.3 只读请求的优化**

+ 如果 Follower 直接读，可能读到旧数据。
+ 两种方案：
    - **Read Index**：读请求先问 Leader 当前 commitIndex，Follower 等自己的 applyIndex ≥ commitIndex 后再返回。
    - **Lease Read**：Leader 在心跳周期内保证自己仍是 Leader（租约），直接读本地状态机，零网络开销。心跳间隔 < 租约时间。

**4. 为什么 Raft 比 Paxos 更易实现**

+ **模块分解（Decomposition）**：Raft 将一致性拆为选举、日志复制、安全性三个独立子问题；Multi-Paxos 缺乏这种清晰的分解。
+ **强领导（Strong Leader）**：日志单向流动（Leader → Follower）简化推理；Paxos 的每个节点都可以提议。
+ **工程化友好**：Raft 论文直接给出了成员变更、日志压缩的实现方案；Paxos 在这些工程细节上留给实现者，导致各实现差异巨大。

**5. P7 面试应用**

+ 能说出 etcd/Consul/TiKV 基于 Raft，ZooKeeper 基于 ZAB。
+ 能比较 Raft vs ZAB 的核心差异（见 Q3）。
+ 如果自研协调器，优先选择 Raft：社区活跃、语言实现多、工程方案成熟。

### Q3：ZAB 协议与 Raft 的主要区别？ZooKeeper 是如何实现分布式一致性协调的？
**A：**

**1. ZAB（ZooKeeper Atomic Broadcast）协议**

+ 专为 ZooKeeper 设计，核心是**原子广播**——保证集群中 Server 的状态变更以相同顺序被应用。
+ 两种运行模式：
    - **恢复模式（Recovery）**：Leader 崩溃后选出新 Leader，同步数据。
    - **广播模式（Broadcast）**：Leader 将事务请求广播给所有 Follower。

**2. 与 Raft 的详细对比**

| 对比维度 | Raft | ZAB |
| --- | --- | --- |
| **日志提交** | Leader 只提交当前 Term；之前 Term 的日志通过当前 Term 日志间接提交 | Leader 可以直接提交之前任期的日志（只要已复制到多数派） |
| **Leader 资格** | 必须日志最新 | 不要求最新，但恢复阶段会强制同步 |
| **日志恢复** | Follower 与 Leader 不一致时，Leader 逐条回退找到一致点再覆盖 | 新 Leader 直接用自己的日志覆盖所有 Follower 的旧日志（包括可能已提交的） |
| **事务标识** | Term + Index | Zxid（高 32 位 epoch + 低 32 位计数器） |
| **设计哲学** | 保守、安全第一 | 更激进，恢复更快但有"模糊提交"风险 |


**ZAB 的"模糊提交"问题**：因为 ZAB 允许新 Leader 覆盖 Follower 上的日志（即使某些 Follower 已经提交了旧 Leader 的部分日志），这意味着：一个已被部分节点提交的日志可能在新 Leader 时期被丢弃。相比之下，Raft 通过 Leader Completeness 保证所有已提交日志永不丢失。

**3. ZooKeeper 的协调机制**

+ **数据模型**：树形 ZNode，类似文件系统。支持持久节点、临时节点（客户端断开自动删除）、顺序节点（自动递增后缀）。
+ **Watcher**：一次性触发器，客户端注册后关注 ZNode 变化。避免轮询，但要注意"一次性"意味着每次触发后需重新注册。
+ **读写分离**：写走 Leader，读可从 Follower（但非 sync 读可能读到旧数据）。`sync()` 调用可强制 Follower 与 Leader 对齐。
+ **分布式锁**：临时顺序节点 + 监听前一个节点的 Watcher → 避免惊群效应（Herd Effect）。

**4. ZooKeeper 的性能天花板 — P7 必须知道**

+ 写操作全部走 Leader，**写性能不随节点数增加而提升**，单集群 TPS 上限约 **1~3 万**（取决于数据大小和网络）。
+ 读操作可水平扩展（加 Follower），但要注意**顺序一致性**语义。
+ 不适合作为高吞吐写的存储，适合**配置管理、服务发现（节点数 < 10 万）、分布式锁/选举**等协调场景。

**5. P7 选型思考**

+ ZK → 稳定、久经考验、CP 保障强，但性能有限、运维重（JVM、磁盘）。
+ etcd → Raft 实现清晰、API 简洁（gRPC+HTTP）、K8s 原生集成、Go 语言运维友好。
+ Consul → 多数据中心 Gossip + Raft、健康检查、服务发现一体。
+ **选型法则**：已有 ZK 技术栈且规模不大 → 沿用。新项目云原生 → etcd。需要多 DC 服务发现 → Consul。

### Q3.5（补全 — Gossip 与 EPaxos）：Gossip 协议的原理与适用场景？EPaxos 解决了什么问题？
**Gossip 协议 — 最终一致的传播机制**

Gossip是去中心化信息传播协议，节点间随机交换信息，O(log N)轮后全网收敛。

特征：去中心化(无Leader单点故障不影响)、最终一致、容错性强。

| 系统 | Gossip 用途 |
| --- | --- |
| **Cassandra** | 集群成员管理、数据副本位置发现 |
| **Consul** | 服务发现 + 健康检查（Serf Gossip 层） |
| **Redis Cluster** | 节点间 PING/PONG 传播 slot 映射和节点状态 |
| **Dynamo** | 副本同步、故障检测 |


**EPaxos — 无 Leader 的 Paxos 变体**

传统Multi-Paxos/Raft所有写必须经过Leader→Leader是性能瓶颈+单点。EPaxos创新：无Leader，任何节点都可提议。通过"命令依赖图"跟踪冲突，无冲突的并发写各自独立提交→吞吐量翻倍；有冲突时通过额外共识轮次解决。

| 协议 | Leader | 并发写 | 适用 |
| --- | --- | --- | --- |
| Raft | 单Leader | 串行 | 简单可靠，通用 |
| Multi-Paxos | 单Leader | 串行 | 理论完善 |
| **EPaxos** | 无Leader | 并行(无冲突时) | 高吞吐、跨地域 |


> EPaxos不是替代Raft的通用方案，而是在高并发写+跨地域延迟敏感场景下的优化选择。

### Q4：分布式唯一 ID 生成方案有哪些？Snowflake 算法原理及时钟回拨如何处理？美团 Leaf 的设计思想？
**A：**

**1. 常见方案五维对比**

| 方案 | 全局唯一 | 趋势递增 | 单调性 | 可读性 | 性能 |
| --- | --- | --- | --- | --- | --- |
| **UUID v4** | ✅ | ❌ 完全无序 | ❌ | ❌ 无含义 | 极高（本地生成） |
| **DB 自增** | ✅ | ✅ 严格递增 | ✅ | ❌ | 低（单点 ~5000/s） |
| **DB 号段（Leaf）** | ✅ | ✅ 趋势递增 | 号段内单调 | ❌ | 高（本地分配） |
| **Redis INCR** | ⚠️ 持久化可能重复 | ✅ 严格递增 | ✅ | ❌ | 高（~10 万/s） |
| **Snowflake** | ✅ | ✅ 趋势递增 | ⚠️ 同一 ms 内递增 | ⚠️ 含时间戳 | 极高（本地生成） |
| **百度 UidGenerator** | ✅ | ✅ 趋势递增 | ✅ | ❌ | 极高（借鉴 Snowflake，用 DB 分配 workerId） |


> **趋势递增 vs 严格递增**：趋势递增（大致递增但不保证相邻 ID 严格 +1）已满足大部分场景的 B+Tree 索引友好需求；严格递增只在有强排序依赖的场景才需要。
>

**2. Snowflake 算法原理**

+ 64 位 long 型 ID：
    - **1 位** 符号位（0）
    - **41 位** 时间戳（毫秒级，从自定义 epoch 算起，可用约 69 年）
    - **10 位** 工作机器 ID（5 位 datacenter + 5 位 workerId，最多 1024 节点）
    - **12 位** 序列号（单机每 ms 最多 4096 个）
+ 生成逻辑：当前时间戳 == 上次时间戳 → 序列号+1（超 4095 阻塞到下一毫秒）；时间戳不同 → 序列号归零。

**3. 时钟回拨 — 故障推演法**

> 🎯 场景：生产环境机器 A 经 NTP 校时，时钟回拨 10 秒，恰好在"被回拨掉"的 10 秒内产生了 5000 个订单号。各方案会怎样？
>

| 方案 | 行为 | 后果 |
| --- | --- | --- |
| 默认 Snowflake | 时间戳回落 → 序列号归零 → **可能生成与之前相同的 ID** | ❌ 订单号重复 |
| 阻塞等待 | 检测到回拨，sleep 直到时间追上 | ⚠️ 10s 内服务不可用（不可接受） |
| 切换 workerId | 检测到回拨，自动分配新 workerId（通过 ZK/DB） | ✅ ID 不重复，可用性不受影响 |
| 美团 Leaf-snowflake | ZK 持久化时间戳，启动时比对，回拨则报警 + 手动修复 | ⚠️ 需人工介入，但安全 |


**推荐策略**：回拨 < 5ms → 等待；回拨 > 5ms → 自动切 workerId + 告警。同时在 NTP 侧配置**慢校时**（slew mode），避免跳跃式校时。

**4. 美团 Leaf 设计思想**

+ **Leaf-segment（号段模式）**：
    - 从 DB 批量拉取号段（step=1000），本地内存分配，用完再取下一个号段。
    - **双 Buffer 优化**：当前号段消耗到阈值时，异步加载下一个号段到备用 buffer，切换零延迟。
    - 动态调整 step：热点业务加大 step 减少 DB 访问；冷业务减小 step 避免浪费。
+ **Leaf-snowflake（雪花模式）**：
    - ZK 注册 workerId，时间戳定期上报 ZK。
    - 启动时与 ZK 记录的时间戳对比 → 回拨报警暂停。
    - 弱依赖 ZK：ZK 不可用时 workerId 使用本地缓存的，保证可用性。

**5. P7 选型决策**

+ 订单号、流水号 → 雪花算法（趋势递增、全局唯一、高性能），配合 workerId 自动分配机制。
+ 用户 ID、商户 ID → Leaf-segment（号段模式），可让 ID 有业务含义（如加上前缀区分用户类型）。
+ 跨机房部署 → 关注 workerId 分配管理（每个机房的 datacenterId 独立），时钟监控统一。

### Q5：分布式锁的常见实现及对比？Redis、ZooKeeper、etcd 各自的锁原理，如何选择？
**A：**

**1. 三种锁方案原理**

**1.1 Redis 锁**

+ 单实例：`SET lock_key random_value NX PX 30000`
+ 释放：Lua 脚本 `if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`（保证原子性 + 只能释放自己的锁）。
+ 续期：**Watchdog（看门狗）**（如 Redisson）— 自动续期直到业务完成，避免业务未完成锁已过期。
+ 集群：**Redlock** — 向 N 个独立 Redis 节点（通常 5 个）依次申请锁，在超时时间内在半数以上节点获锁成功即为成功；释放时向所有节点删除。

**1.2 ZooKeeper 锁**

+ 原理：临时顺序节点 + Watcher 前驱监听。
    1. 所有竞争者在该锁 ZNode 下创建临时顺序子节点，获得序号。
    2. 获取所有子节点排序，序号最小者获得锁。
    3. 未获得锁者对**前一个**节点注册 Watcher（监听删除），而非监听所有节点——**避免惊群效应**。
    4. 释放：删除自己的临时节点（客户端断开时自动删除）。

**1.3 etcd 锁**

+ 类似 ZK：利用 Lease（租约）+ 事务，原子性创建带租约的 key。通过 Revision（全局递增版本号）实现 FIFO 公平锁。

**2. Fencing Token — P7 分水岭 �***

**问题**：即使 Redis/ZK/etcd 提供了安全的分布式锁，**锁持有者的执行延迟**（GC 停顿、网络延迟、CPU 抢占）仍可能导致安全性问题：

```plain
时间轴:
T1: Client A 获锁，token=33
T2: Client A GC 停顿 5s，锁超时释放
T3: Client B 获锁，token=34，开始写存储
T4: Client A GC 恢复，用 token=33 写入存储 ← 破坏了 B 的写入！
```

**解决方案 — Fencing Token**：锁服务返回一个**单调递增的 token**，资源层（存储）拒绝小于当前已见最大 token 的写入请求。这要求**存储层配合**（如利用 DB 的 WHERE token > last_token）。

> 在 P7 面试中，能主动提及 Fencing Token 是区分"背诵方案"和"深入理解分布式安全"的关键标志。
>

**3. Redlock 争议深入 — 展示批判性思维**

**Martin Kleppmann 的批判**（《How to do distributed locking》）：

+ Redlock 假设时钟是安全的，但**时钟跳变**（NTP 大步调整）和**进程暂停**（GC）会破坏互斥。
+ Redlock 没有 Fencing Token 机制，持有锁的客户端可能因为延迟而"活在过去"。
+ **结论**：如果你需要锁的正确性，Redlock 不够；如果不需要正确性，用单机 Redis 锁就行（加幂等兜底即可）。

**Antirez（Redis 作者）的回应**：

+ Redlock 的设计模型假设时钟误差可控（NTP 正常运行、GC pause 不会太长），在绝大多数生产场景下是安全的。
+ Fencing Token 是更好的方案，但需要存储配合；Redlock 提供了不需要改存储层的折中方案。

> **P7 面试回答**：先陈述双方论点，再给出自己的判断——「对于非资金类业务（如防止重复操作、秒杀限流），Redlock 够用；对于资金类业务，用 ZK/etcd + Fencing Token，或在 DB 层加乐观锁作为最后防线」。
>

**4. 性能定量对比**

| 方案 | 加锁延迟 | 解锁延迟 | 安全性 | 自动续期 |
| --- | --- | --- | --- | --- |
| Redis 单机 | ~1ms | ~0.5ms | ⚠️ 主从切换丢锁 | 看门狗 |
| Redlock | ~5ms | ~3ms | ⚠️ 有时钟依赖 | 需自行实现 |
| ZooKeeper | ~10ms | ~5ms | ✅ 强一致 | 临时节点 |
| etcd | ~8ms | ~4ms | ✅ 强一致 | Lease/TTL |


**5. 锁的容灾矩阵 — P7 决策能力**

| 故障场景 | 策略 | 实现要点 |
| --- | --- | --- |
| Redis 集群不可用 | 降级到 ZK/etcd 锁 | 配置中心动态切换，熔断自动降级 |
| ZK/etcd 不可用 | 降级到 DB 悲观锁（`SELECT ... FOR UPDATE`） | 仅在极端情况使用，性能较差但正确性最高 |
| 业务 GC 停顿 > 锁超时 | Fencing Token 防护 | 存储层校验 token 单调性 |
| 锁服务全挂 | 业务拒绝写入，快速失败 | 宁可不可用，不能出错（资金类） |


**6. 选型原则**

+ **秒杀、幂等防护**（可容忍极小概率重复）→ Redis + 幂等兜底
+ **资金、账户、排他操作**（强一致必须）→ ZK/etcd + Fencing Token
+ **云原生、K8s 环境** → etcd（K8s 原生集成）

### Q6：如何设计一个支持全局唯一性约束的分布式系统？（如防止账号重复注册）有哪些策略？
**A：**

**1. 核心挑战**

+ 高并发下保证某个字段（如手机号）全局唯一。
+ 不能成为性能瓶颈（不能全局锁或单点校验）。

**2. 从简到优：演进式方案推演**

**V1：直击痛点 — 数据库唯一索引**

+ 最可靠，但严重问题：
    - 单表数据量上百亿后索引性能下降。
    - 分库分表后**跨分片的唯一性约束失效**。

**V2：哈希分片路由表**

+ 建立一张「手机号 → 用户 ID 分片映射表」，以手机号哈希分片。
+ `INSERT INTO routing_table (phone_hash, phone, user_id) VALUES (hash(phone), phone, uid)`
+ 分片表和用户表按同样哈希算法分片，保证每个用户的全部数据在同一分片。
+ **问题**：热点手机号仍可能集中。

**V3：多级防护体系 — 最终推荐方案**

```plain
请求
  │
  ▼
┌─────────────────────┐
│ ① 布隆过滤器        │ ← 快速"可能不存在"判断
└──────┬──────────────┘
       │ 不存在
       ▼
┌─────────────────────┐
│ ② Redis SETNX       │ ← 二级快速去重（毫秒级）
└──────┬──────────────┘
       │ 设置成功
       ▼
┌─────────────────────┐
│ ③ DB 唯一索引(兜底) │ ← 绝对可靠保证
└─────────────────────┘
```

+ **布隆过滤器**：快速过滤"一定不存在"的请求，减少 Redis/DB 压力。
    - **误判率计算公式**：p ≈ (1 - e<sup>{-kn/m})</sup>k，其中 k 为哈希函数个数，m 为位数组大小，n 为元素数量。
    - 实例：1 亿手机号，误判率 0.1% → 约 1.2GB 内存。
    - **定期重建**：每天凌晨从 DB 全量重建，或在写入时同步更新。
+ **Redis**：`SETNX phone:138xxxx`，前置快速判断，TTL 根据注册流程时长设置。
+ **DB 唯一索引**：最终防线。对 `phone_hash` 建唯一索引（而非 `phone` 明文），配合 `INSERT ... ON DUPLICATE KEY` 处理冲突。

**3. 扩容平滑迁移**

+ 从 16 库扩到 32 库，唯一性约束如何保持？
    - **方案**：先双写（新旧分片同时写入、两套唯一索引独立保证），数据全量迁移后，逐步切读流量 → 撤旧分片。
    - 迁移过程中，使用新旧路由映射表，查询时先查新 → 没有则查旧。

**4. P7 视角**

+ 能估算容量（亿级用户）并计算存储和 QPS。
+ 能说明为什么不推荐用分布式锁（每个手机号一把锁，锁总数 = 用户数，管理不可行）。
+ 能补充 Redis 和 DB 数据不一致时的兜底（最终一致 + DB 唯一索引为最强保证）。

### Q7：跨机房部署如何实现同城双活与异地多活？面临哪些技术挑战？
**A：**

**1. 同城双活（两地三中心之同级）**

+ **前提**：同城距离 < 100km，光纤延迟 1~3ms，可视为近实时。
+ **架构**：
    - 数据层：MySQL MGR（Group Replication）或分布式数据库（TiDB/OceanBase）多副本跨机房同步。Redis Cluster 跨机房主从。
    - 接入层：DNS/GSLB → 就近流量分发。服务注册中心（Nacos）分区感知，优先调用同机房服务。
    - 网关：跨机房负载均衡，单机房故障自动切换。

**2. 异地多活（不同城市）**

+ **现实约束**：异地延迟 > 30ms，无法做强同步写入，必须接受**最终一致**。
+ **数据方案**：
    - **单元化（Unit）架构**：用户按 ID 哈希固定路由到一个单元（机房），所有数据在该单元内强一致，跨单元只做异步备份。这是阿里核心架构模式。
    - **最终一致多写**：各机房都有全量数据，写操作各自本地写入，异步同步。需处理**写冲突**。

**3. 数据冲突解决策略对比（P7 核心）**

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| **LWW（Last Write Wins）** | 按时间戳比较，最新覆盖 | 简单 | 可能丢数据（并发写入只有一个保留） | 用户配置、缓存 |
| **版本向量（Vector Clock）** | 维护各节点的逻辑时钟向量，判断因果/并发关系 | 能识别因果关系 | 冲突需业务处理，实现复杂 | Dynamo、Riak |
| **CRDT** | 数据结构本身保证合并结果唯一 | 自动合并，理论完善 | 数据类型受限 | 计数器、集合、协作编辑 |
| **业务自定义合并** | 根据业务语义编写合并逻辑 | 最灵活 | 开发成本高 | 订单、交易 |
| **单元化（避免冲突）** | 让冲突不发生 | 无冲突 | 路由复杂度高 | 用户维度的数据 |


**4. 单元化路由设计**

+ 用户 → 单元映射存储于全局配置中心（如 Nacos）。
+ 路由变更（用户迁移）→ 双写过渡期 + 数据迁移 + 路由切换 + 清理旧数据。
+ **安全边界**：任何时刻，一个用户的数据只有一个单元可写。

**5. 异地多活的反模式（P7 要敢于说"不"）**

+ 异地多活不是银弹：**带来的是数倍的架构复杂度和运维成本**。
+ 很多公司"异地多活"实际上是：**同城双活 + 异地灾备（冷备）**，这才是成本与可用性的合理折中。
+ 真正需要异地多活的场景：DAU 过亿、数据量 PB 级、监管要求数据本地化（GDPR）、或灾难时要求 RPO=0 的核心系统。
+ **P7 面试策略**：不被面试官的"假需求"带偏，能基于成本收益分析给出务实的方案。

**6. P7 视角总结**

+ 能说出同城双活的技术细节（MGR、路由、故障切换）。
+ 能清醒评估异地多活的真实成本，知道何时该做、何时不该做。
+ 能定义 RTO（恢复时间目标）和 RPO（数据丢失容忍度），并据此选择灾备级别。

### Q8（P7 情景题）：设计一个大规模分布式系统，如何进行容量规划和数据一致性保障？
**A：**

此类开放题考察从 0 到 1 的系统设计能力。以下为 P7 级回答框架：

**1. 需求量化**

| 维度 | 指标 | 示例 |
| --- | --- | --- |
| 用户规模 | DAU / MAU | 1000 万 DAU |
| 峰值 QPS | DAU × 人均请求 / 时间 × 峰值系数 | 1000万 × 20次 / 86400s × 5 峰 = **~1.2万 QPS** |
| 日增数据 | 日增订单量 × 每单存储 | 500万 × 2KB = **10GB/天** |
| 峰值 TPS | 核心交易链路 | 5000 TPS（写） |
| 延迟要求 | p99 / p999 | p99 < 200ms, p999 < 1s |
| 可用性 | 全年不可用时间 | 99.99%（≈53分钟/年） |


**容量估算核心公式：**

```plain
峰值 QPS = (DAU × 人均请求次数) / 86400 × 峰值系数(3~5x)

存储容量 = 日增数据 × 保留天数 × 副本数 × 1.5(索引开销)

带宽 = QPS × 平均响应大小(bytes) × 8 / 压缩比

单机 QPS 参考值：
  Nginx: ~10万 QPS
  Java 微服务: ~5000-20000 QPS（取决于业务复杂度）
  MySQL 单库: ~5000 QPS（读多写少）
  Redis 单实例: ~10万 QPS
```

**2. 架构分层规划**

| 层 | 组件 | 容量考量 | 高可用 |
| --- | --- | --- | --- |
| 接入层 | DNS → LVS/F5 → Nginx/API Gateway | 单 Nginx 10万+ QPS，按峰值冗余 3 倍 | 多机房、健康检查 |
| 服务层 | 无状态微服务（容器化） | 所需实例数 = 峰值 QPS / 单实例 QPS，预留 3x | K8s HPA 自动扩缩、限流熔断降级 |
| 缓存层 | Redis Cluster | 按内存量（总数据 × hash 分片）和 QPS 确定分片数 | 哨兵/Cluster、异地多副本 |
| 数据库 | MySQL 分库分表 | 单表 < 2000万行，按 QPS 和存储确定分片数 | 主从、MGR、DTS |
| 消息队列 | RocketMQ/Kafka | 按峰值 TPS 定分区数，保证写入和消费不堆积 | 多副本、自动 failover |


**3. 数据一致性保障策略矩阵**

| 场景 | 方案 | 兜底 |
| --- | --- | --- |
| 服务内操作 | 本地事务（ACID） | — |
| 同步跨服务调用 | 幂等 + 重试 + 超时控制 | 对账发现异常 |
| 异步跨服务（常规） | MQ + 本地消息表/事务消息 | 定时对账、死信队列重试 |
| 关键数据（资金/库存） | TCC 或 AT 分布式事务 | 对账 + 人工处理 |
| 缓存一致性 | Cache Aside + Binlog 异步刷新 + 短过期兜底 | 双删 + MQ 重试 |
| 多机房数据 | 单元化（避免冲突）或异步同步 + 版本向量 | 跨机房对账 |


**4. 完整对账体系设计**

+ **实时对账**（秒级~分钟级）：核心资金流水，消息队列驱动的准实时核对。
+ **T+1 对账**（隔日）：全量数据比对，发现差异后分级处理。
+ **差异分级**：
    - P0（资金不一致）→ 立即人工介入 + 暂停相关账户操作
    - P1（数据不一致可自动修复）→ 自动补偿任务
    - P2（可容忍的延迟一致）→ 记录日志，等待下次对账

**5. 降级策略矩阵**

+ 缓存不可用 → 穿透到 DB，限流保护
+ DB 主库不可用 → 从库顶上，禁写
+ MQ 堆积 → 消费者动态扩容，生产者限流
+ 分布式事务协调器不可用 → 切换异步消息兜底

**6. 案例推演：日均百万订单系统**

> 峰值 QPS 5000。16 库 × 16 表按 user_id 分片。Redis Cluster 缓存热点商品。RocketMQ 异步处理订单后续流程。同步扣库存用 Redis Lua + DB 最终扣减，对账保证一致。
>

**P7 亮点**：有公式、有数字、有冗余考量、有降级预案、有对账兜底。不是"用这个就行"，而是"用这个是因为算过了，出问题时还有这个兜底"。

### Q9：常见的分布式调度框架有何不同？如何自己实现一个分布式任务调度系统？
**A：**

**1. 框架对比**

| 框架 | 模式 | 协调方式 | 优点 | 缺点 | 适用团队 |
| --- | --- | --- | --- | --- | --- |
| **Quartz** | 单机 + DB 锁伪分布 | DB | 简单，上手快 | 无分片，扩展性差 | 小型项目 |
| **Elastic-Job** | 去中心化 | ZK | 分片灵活，弹性扩缩，failover 自动 | ZK 依赖，性能有上限 | 中型项目，任务需分片 |
| **XXL-JOB** | 中心化 Admin | DB | 管理方便，可视好，接入简单 | Admin 单点风险 | 中小团队首选 |
| **SchedulerX** | 中心化（阿里云） | 云原生 | MapReduce 模型，高可用，免运维 | 商业收费，云绑定 | 阿里云客户 |


**中心化 vs 去中心化选型原则：**

+ **中心化（XXL-JOB）**：易于监控管理、任务可视化、统一调度；Admin 需高可用，否则单点故障影响所有任务。
+ **去中心化（Elastic-Job）**：可靠性高（无单点）、分片绑定执行器、failover 自动；运维成本高（ZK 集群）。
+ **中小企业推荐**：XXL-JOB 二次开发，成本低、见效快；大团队自研可参考 Elastic-Job 思想。

**2. 自研调度系统核心设计**

**组件架构：**

```plain
Scheduler(主) → ZK 选主
     │
     ├─→ 任务管理 DB（MySQL）
     ├─→ 时间轮 + DB 扫描触发
     └─→ Worker(多实例) 执行任务
              │
              └─→ ZK 分片绑定
```

+ **任务分配**：通过 ZK 临时节点绑定分片 → 执行器的映射。执行器宕机 → 临时节点删除 → 分片自动迁移到其他执行器。
+ **触发机制**：时间轮（HashedWheelTimer）+ DB 任务表二级调度。调度中心扫描即将到期任务 → 入时间轮 → 精确秒级触发 → 下发 Worker。
+ **高可用**：调度中心多实例 + ZK 选主（主负责调度，从待命）。Worker 无状态，水平扩展。

**3. 任务幂等性保证 — P7 必须考虑**

+ 任务执行到一半宕机，重试时怎么办？
    - **方案 1**：任务表记录状态机（待执行 → 执行中 → 成功/失败/超时），重试前检查状态。
    - **方案 2**：业务侧幂等设计（如携带唯一 requestId，重复执行返回相同结果）。
    - **方案 3**：任务分片绑定 + 心跳，如果分片已迁移给其他执行器，原执行器不再执行。

**4. 故障演练**

+ **调度中心挂了**：选主毫秒级完成，新主从 DB 恢复待调度任务，时间窗口内任务延迟但不丢失。
+ **执行器宕机**：持有分片 → 心跳超时 → ZK 临时节点消失 → 分片重新分配给其他执行器 → 任务在新执行器重试。
+ **任务堆积**：监控队列深度 → 自动扩容 Worker → Worker 就位后分片重新分配。

**5. P7 面试策略**

+ 能对比中心化和去中心化的取舍，不是背诵优劣。
+ 能画出自研系统的架构图，并解释各组件选型原因。
+ 能说清楚异常场景下的系统行为（不是只说"会高可用"）。

### Q10（新增）：分布式事务有哪些方案？2PC/3PC/TCC/Saga/AT/消息事务各自的原理、优劣和适用场景？
**A：**

**1. 从刚性到柔性：分布式事务方案谱系**

```plain
强一致 ←──────────────────────────→ 最终一致

2PC/3PC → AT(Seata) → TCC → Saga → 本地消息表 → 事务消息(可靠消息)
（刚性事务）              （柔性事务）
```

**2. 刚性事务**

**2.1 2PC（Two-Phase Commit / XA 协议）**

+ **阶段 1（Prepare）**：协调者询问所有参与者是否准备好提交。
+ **阶段 2（Commit/Rollback）**：协调者根据所有参与者反馈决定全局提交或回滚。
+ **致命缺陷**：
    - 协调者单点故障 → 参与者阻塞在 Prepare 状态，锁资源不释放。
    - 参与者同步阻塞，性能差。
    - 部分提交失败时无回滚机制（参与者已提交，无法撤回）。
+ **适用**：同数据库跨表操作；跨系统的场景基本不适用。

**2.2 3PC（Three-Phase Commit）**

+ 在 2PC 的 Prepare 和 Commit 之间插入 **PreCommit** 阶段，引入超时机制缓解阻塞。
+ 仍无法完全解决网络分区时的不一致问题（部分收到 Commit，部分没收到）。
+ 实际使用极少，主要作为理论改进讨论。

**3. 柔性事务**

**3.1 AT 模式（Seata AT — Automatic Transaction）**

+ 自动生成回滚日志（undo log），业务代码无侵入。
+ 一阶段执行 SQL 并记录 undo log；二阶段成功则删除 undo log，失败则用 undo log 回滚。
+ **优点**：对业务零侵入，改造成本低。
+ **缺点**：依赖数据库，有脏写风险（全局锁解决，但影响性能）。
+ **适用**：改造老系统，不想大改业务代码。

**3.2 TCC（Try-Confirm-Cancel）**

+ **Try**：预留资源（冻结库存、预扣金额）。
+ **Confirm**：确认提交（扣库存、完成扣款）。
+ **Cancel**：释放预留资源（解冻库存、退款）。
+ **优点**：不依赖数据库锁，性能好，业务灵活。
+ **缺点**：代码侵入大，需为每个资源实现 Try/Confirm/Cancel 三个接口；Cancel 的幂等和空回滚处理复杂。
+ **适用**：资金、库存等核心场景，需要精确控制。

**3.3 Saga 模式**

+ 将长事务拆为多个有序的本地事务，每个本地事务有对应的**补偿操作**。
+ 两种实现：
    - **编排式（Choreography）**：事件驱动，每个服务完成后触发下一个。
    - **控制式（Orchestration）**：中央 Saga 协调器调用各服务。
+ **优点**：无全局锁，高并发；适用于长事务（几分钟到几天）。
+ **缺点**：补偿复杂（一个步骤失败需要反向补偿前面所有步骤），缺乏隔离性。
+ **适用**：跨服务的长时间业务流程（如旅行预订系统）。

**3.4 本地消息表 + 事务消息**

**本地消息表（eBay 模式）**：

+ 在业务数据库中建一张消息表，与业务数据在同一本地事务中写入。
+ 定时的后台任务扫描消息表，发送到 MQ。
+ 消费方幂等消费，反馈消费结果。
+ **优点**：实现简单，可靠。
+ **缺点**：消息表和业务表耦合在同一数据库，扩展时需带历史数据。

**事务消息（RocketMQ 实现）**：

+ 发送半消息（Half Message）→ 执行本地事务 → 根据事务结果提交或回滚消息。
+ RocketMQ 会定时反查生产者确认事务状态。
+ **优点**：消息和业务解耦，可靠性高。
+ **缺点**：依赖 RocketMQ，需实现反查接口。

**4. 方案选型决策树**

```plain
需要跨服务的事务？
  │
  ├── 强一致必须，允许短时间锁等待？
  │     └── Seata AT（改造成本低）
  │
  ├── 资金/库存扣减，需要精确回滚？
  │     └── TCC（灵活性强，代码侵入大）
  │
  ├── 长流程（分钟~天级），可接受最终一致？
  │     └── Saga + 补偿
  │
  └── 异步解耦场景，不需要同步等待？
        └── 事务消息（RocketMQ）或本地消息表
```

**5. P7 面试视角**

+ 能画出一致性谱系图（2PC → AT → TCC → Saga → 消息 → 对账），说明各方案的"刚度"递减。
+ 能结合业务说"这个场景用了 TCC，因为需要精确回滚和 Cancel 的幂等性"。
+ 能说出分布式事务的**实际生产痛点**：空回滚、悬挂、幂等、补偿的死循环、超时处理。
