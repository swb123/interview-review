### Q1：InnoDB 的 B+Tree 索引结构是怎样的？聚簇索引和二级索引有何区别？什么是回表、覆盖索引和索引下推？
**A：**

**1. B+Tree vs B-Tree — 为什么 MySQL 选择 B+Tree？**

| 维度 | B-Tree | B+Tree |
| --- | --- | --- |
| 数据存储 | 所有节点都存数据 | 仅叶子节点存数据 |
| 非叶子节点 | 占用空间大，每个节点存的关键字少 | 只存键+指针，树更矮 |
| 范围查询 | 需要中序遍历，跨层访问 | 叶子节点有双向链表连接，顺序遍历 O(n) |
| 磁盘 IO | 每 IO 读取的有效键少 | 每 IO 读取更多键 |


B+Tree 高度计算：2000 万行，bigint 主键（8字节）+ 指针（6字节）= 14字节/条目。16KB 页 ≈ 1170 个条目。树高 3 层：1170^2 × 16 ≈ 2,190 万行 ≈ 3 次 IO 即可定位。

**2. 聚簇索引 vs 二级索引**

聚簇索引叶子节点存完整行数据，二级索引叶子节点存索引列+主键值。回表：二级索引→聚簇索引再查一次。覆盖索引：查询列全在索引中，无回表。索引下推（ICP）：存储引擎用索引列过滤 WHERE，不满足的连回表都省了。

**3. 页分裂与页合并**：插入时页满→分配新页→移动50%数据；删除后填充率低于50%→相邻页合并。UUID主键导致频繁页分裂→性能下降，推荐自增主键。

**4. explain 完全解读**：type(const>eq_ref>ref>range>index>ALL)、key(实际使用)、rows(预估扫描)、Extra(Using index/filesort/temporary)。

**5. 最左前缀原则**：联合索引(a,b,c) — WHERE a=1走索引，WHERE b=2不走。P7追问：WHERE a>10 AND b=5 仅a列走索引。

### Q2：如何优化分页查询 LIMIT 100000, 10？多表 JOIN 优化？
**A：**

大 offset 分页三种方案：①子查询定位（SELECT * FROM t JOIN (SELECT id FROM t LIMIT 100000,10) tmp USING(id) — 子查询只扫索引不回表）；②游标翻页（WHERE id>100000 LIMIT 10）；③Elasticsearch。

JOIN 优化原则：小表驱动大表、被驱动表关联列必须有索引、避免对索引列使用函数/运算。STRAIGHT_JOIN强制MySQL按指定顺序JOIN。

子查询改写：IN→semi-join(8.0)、NOT IN→LEFT JOIN/ NOT EXISTS、相关子查询→JOIN。

索引失效场景：对索引列用函数、隐式类型转换、LIKE前模糊、OR含非索引列、跳过最左列。

慢查询分析：pt-query-digest → EXPLAIN FORMAT=JSON → EXPLAIN ANALYZE(8.0)。

### Q3：事务隔离级别有哪些？MySQL 的 MVCC 是如何实现的？
**A：**

四大隔离级别：READ UNCOMMITTED(脏读)、READ COMMITTED(不可重复读)、REPEATABLE READ(InnoDB默认)、SERIALIZABLE(串行)。

MVCC 三组件：隐藏列(DB_TRX_ID + DB_ROLL_PTR) + undo log版本链 + ReadView(m_ids/min_trx_id/max_trx_id/creator_trx_id)。

可见性判断：trx_id==creator→可见；trx_id<min→可见；trx_id>=max→不可见；在m_ids中→不可见。不可见时沿ROLL_PTR回溯版本链。

RC vs RR核心差异：RC每次快照读生成新ReadView→不可重复读；RR复用首次ReadView→可重复读。

当前读(SELECT FOR UPDATE/UPDATE/DELETE)读最新版本+加锁；快照读(普通SELECT)基于MVCC无锁。

### Q4：什么是间隙锁和临键锁？如何解决幻读？UPDATE 语句具体会加哪些锁？
**A：**

**1. InnoDB 四种锁**

+ **Record Lock（行锁）**：锁索引记录本身。
+ **Gap Lock（间隙锁）**：锁索引记录之间的空隙（前开后闭区间），阻止其他事务在间隙内插入——防止幻读的核心。
+ **Next-Key Lock（临键锁）**：行锁 + 间隙锁的组合，InnoDB 默认加锁单位。
+ **Insert Intention Lock（插入意向锁）**：插入前对目标间隙加的特殊锁，互不冲突，仅与间隙锁冲突（产生锁等待）。

**2. 加锁规则：两个原则 + 两个优化 + 一个 bug（RR 隔离级别，面试必背）**

+ **原则 1**：加锁的基本单位是 **next-key lock**（前开后闭区间）。
+ **原则 2**：**查找过程中访问到的对象才会加锁**——没访问到的记录不加锁。
+ **优化 1**：索引上的等值查询，**唯一索引**命中时，next-key lock 退化为**行锁**。
+ **优化 2**：索引上的等值查询，向右遍历时**最后一个值不满足等值条件**，next-key lock 退化为**间隙锁**。
+ **一个 bug**：唯一索引上的**范围查询**，会访问到不满足条件的第一个值为止（多锁一段区间）。

**3. 常见 UPDATE 加锁推演**（表 t 数据：id 主键 = 0,5,10,15,20,25；普通索引 a 同值。以下均为 RR 级别当前读）

| SQL | 加锁过程 | 最终锁范围 |
| --- | --- | --- |
| `UPDATE t ... WHERE id=5` | 唯一索引等值命中 → 优化1 退化为行锁 | id=5 行锁 |
| `UPDATE t ... WHERE id=7` | 唯一索引等值未命中 → 定位到 (5,10) 间隙防插入 | gap (5,10) |
| `UPDATE t ... WHERE a=5`（a 普通索引） | 等值命中 a=5 → next-key (0,5]；向右遍历到 a=10 不满足 → 优化2 退化为间隙锁 | (0,5] + (5,10) |
| `UPDATE t ... WHERE id>=10 AND id<11` | 找到 id=10 → next-key (5,10]；范围查询向右访问到 15（bug：不满足条件也访问） | (5,10] + (10,15] |
| `UPDATE t ... WHERE a>=10 AND a<11`（普通索引范围） | next-key (5,10] → (10,15] → 再访问 20 不满足才停 | (5,10] + (10,15] + (15,20] |
| `UPDATE t ... WHERE b=5`（b 无索引） | 全表扫描，**表中所有记录**都加 next-key lock | 全表锁——最危险！ |


**关键结论**：

+ **UPDATE/DELETE/SELECT FOR UPDATE 都是当前读，加锁规则相同**；普通 SELECT 是快照读，靠 MVCC 无锁。
+ **唯一索引等值**：命中 → 行锁；未命中 → 间隙锁。
+ **普通索引/范围**：锁住的区间比直觉多——面试时能说出「范围查询会向右多访问一条不满足条件的记录」是 P7 分水岭。
+ **无索引的 UPDATE**：InnoDB 退化为全表 next-key 锁，并发写互堵——线上慢 UPDATE 排查时先看是否走了索引。

**4. RC vs RR 加锁差异**

+ RR：完整 next-key 锁体系（行锁 + 间隙锁 + 临键锁），**解决幻读**。
+ RC：**Gap Lock 不生效**（仅行锁，外键检查/唯一键冲突检测等个别场景除外）→ 存在幻读；但死锁概率更低，锁范围小并发更好。
+ 幻读总结：RR 下**快照读由 MVCC 解决，当前读由临键锁解决**；RR 下快照读与当前读混用仍可能"半幻读"→ 一致性要求高时全程当前读。

**5. 死锁排查**

`SHOW ENGINE INNODB STATUS`（LATEST DETECTED DEADLOCK 段）+ `performance_schema.data_lock_waits`（直接给出 KILL 语句）。避免原则：事务短小、固定加锁顺序（按 id 升序）、尽量用唯一索引/覆盖索引减少锁范围。

### Q5：如何设计分库分表？垂直拆分与水平拆分的区别？
**A：**

拆分信号：单表>2000万、单库写TPS>3000~5000、单库>500GB、多业务共库。

垂直拆分（按业务/按列）vs 水平拆分（按行分片）。分片算法：取模(均匀但扩容难)、一致性哈希(扩容易)、范围(可能热点)、复合分片。

逻辑分片 vs 物理实例：先分配4096个逻辑分片，扩容时迁移逻辑分片到新物理库。

ShardingSphere-JDBC架构：SQL解析→路由→改写→执行→结果归并。分片键选择：覆盖90%查询的条件。

### Q6：MySQL 主从复制原理？半同步复制与 MGR 的区别？
**A：**

复制演进：异步→半同步(5.5)→增强半同步(5.7)→MGR组复制(5.7)→并行复制(8.0 WRITESET)。

| 模式 | 数据安全 | 性能影响 | 适用 |
| --- | --- | --- | --- |
| 异步 | 可能丢数据 | 无影响 | 读多写少 |
| 半同步 | 至少一个从库确认 | 主库等ACK | 数据安全要求高 |
| MGR单主 | Paxos多数派提交 | 延迟增加 | 金融级强一致 |
| MGR多主 | 冲突检测 | 冲突需回滚 | 多机房多活 |


并行复制原理：分析binlog中事务修改的行数据，不冲突的事务并行执行→主从延迟从分钟级降到秒级。

GTID(全局事务标识符)：MASTER_AUTO_POSITION=1，从库自动找位点，切换主库无缝。

读写分离一致性：强制走主库(强一致)、半同步复制(<1s窗口)、GTID等待(强一致)、缓存补偿(最终一致)。大部分场景：关键操作后读主库+普通查询半同步容忍。

### Q7：Redis 的 5 种基本类型的内部编码有哪些？
**A：**

| 类型 | 编码(小→大) | 阈值 | 设计考量 |
| --- | --- | --- | --- |
| String | int→embstr→raw | embstr≤44B | 一次malloc vs 两次 |
| List | quicklist(3.2+) | — | ziplist+链表平衡 |
| Hash | ziplist→hashtable | entry≤512且val≤64B | 紧凑→O(1) |
| Set | intset→hashtable | 全整数≤512 | 二分→NULL字典 |
| ZSet | ziplist→skiplist+dict | entry≤128 | 范围+点查 |


embstr vs raw内存布局：embstr一次malloc连续内存、raw两次malloc指针分离。

**Stream (Redis 5.0+) — 轻量级消息队列**

```bash
XADD mystream * field1 value1   # 生产者
XREAD COUNT 2 STREAMS mystream 0  # 消费者
XGROUP CREATE mystream mygroup $  # 消费者组
XREADGROUP GROUP mygroup c1 STREAMS mystream >  # 消费
XACK mystream mygroup <msg-id>  # 确认
```

| 特性 | Redis Stream | Kafka/RocketMQ |
| --- | --- | --- |
| 定位 | 轻量级、嵌入Redis | 重量级、独立部署 |
| 持久化 | 依赖RDB/AOF | 磁盘+副本 |
| 消费组 | ✅ XREADGROUP | ✅ |
| ACK | ✅ XACK | ✅ offset commit |
| 适用 | 轻量消息(千级QPS) | 高吞吐(十万+QPS) |


> P7 选型：Stream 适合不需要额外部署 MQ 的场景，大规模消息仍需专业 MQ。

### Q8：Redis 持久化 RDB 和 AOF 的原理及优缺点？
**A：**

| 维度 | RDB | AOF | 混合持久化(4.0+) |
| --- | --- | --- | --- |
| 原理 | fork子进程COW写快照 | 写命令追加+定期rewrite | RDB头部+AOF增量 |
| 恢复速度 | 极快 | 慢(逐条重放) | 快(RDB+少量AOF) |
| 数据安全 | 丢上次快照后的 | 最多丢1s(everysec) | 最多丢1s |
| 文件大小 | 紧凑(二进制) | 大(文本) | 较大 |
| 性能影响 | fork阻塞+COW内存翻倍 | everysec轻微 | 同AOF |


RDB COW风险：父进程大量写入→触发大量COW→内存可能翻倍→OOM。

AOF重写：分析当前内存快照→生成等价的更小命令集。

生产推荐：缓存→RDB；持久化数据→混合持久化+AOF everysec；极高安全→AOF always+RDB+从节点。

### Q9：Redis 过期键删除策略与内存淘汰策略？
**A：**

过期删除：惰性删除(访问时检查+过期即删) + 定期删除(每秒10次随机抽20个key，过期比例>25%继续本轮，单次<25ms)。

淘汰策略：allkeys-lru(通用缓存)、allkeys-lfu(冷热分明)、volatile-lru(有永久数据)、volatile-ttl(即将过期的先淘汰)、noeviction(拒绝淘汰)。

近似LRU：随机采样N个key淘汰最久未访问的(maxmemory-samples默认5)。LFU实现：24位lru字段，高16位访问时间+低8位对数计数器(概率递增+随时间衰减)。

### Q10：Redis 主从、哨兵、集群模式架构及原理？
**A：**

| 维度 | 主从 | 哨兵 | Cluster |
| --- | --- | --- | --- |
| 数据分布 | 全量每节点 | 全量每节点 | 16384 slot分片 |
| 故障转移 | 手动 | 哨兵自动选主 | 内置Gossip投票 |
| 水平扩展 | 不能 | 仅读扩展 | 在线reshard |
| 适用规模 | <10GB | <10GB | TB级 |


哨兵：PING监控→SDOWN→ODOWN(quorum)→Raft选主→新主选举(优先级>偏移量>runid)。16384 slot原因：足够均匀+CRC16计算快+心跳位图2048字节合理。

### Q11（场景题）：千万级用户订单表如何拆分？双 11 动态扩容方案？
**A：**

容量规划：日均500万、累计20亿+、峰值QPS 10000写/30000读、存储约1TB。方案：4096逻辑分片、16实例(每实例256分片)、单库约63GB。分片键user_id，商家侧异构同步ES。

订单表结构：主表(高频小字段+idx_user_id_status)、扩展表(低频大字段detail/snapshot)。

双11迁移：T-3月压测→T-1月新库+全量同步→T-1周对账完成→T当天监控+应急。ShardingSphere Scaling：配置源端目标端→全量SELECT+INSERT→增量binlog→CRC对账→灰度1%→10%→50%→100%。风险：数据不一致(三次CRC)、影响线上(限速+深夜)、需回滚(保留旧库7天)。

### Q12（新增 — MySQL 性能排障）：数据库 CPU 飙高、慢查询增多、锁等待严重时如何系统性排查？
**A：**

①先看全局指标(Prometheus)：QPS/TPS/连接数/主从延迟/buffer pool命中率 ②定位类别→分步骤排查。

CPU飙高：SHOW FULL PROCESSLIST + sys.statement_analysis + sys.schema_tables_with_full_table_scans。根因：全表扫描、排序未用索引、锁竞争自旋、刷脏页。

慢查询定位：sys.statements_with_full_table_scans + sys.io_global_by_file_by_bytes + EXPLAIN ANALYZE(8.0实际执行耗时)。

锁等待排查：sys.innodb_lock_waits(直接给出KILL命令) + performance_schema.data_locks + data_lock_waits。

IO瓶颈：sys.io_global_by_file_by_bytes + buffer pool命中率(低于95%→扩容)。

### Q14（新增 — SQL 基础高频题）：数据库三大范式、CHAR 与 VARCHAR 的区别、如何避免重复插入、SQL 语句的执行顺序？外键为什么在生产中禁用？
**A：**

**三大范式**：1NF 列不可再分；2NF 消除非主属性对主键的部分依赖（联合主键场景）；3NF 消除传递依赖（非主属性不依赖其他非主属性）。生产实践常反范式化：冗余字段减少 JOIN，一致性靠应用层保证。

**CHAR vs VARCHAR**：CHAR 定长（0 至 255 字符，固定存储空间，读写快，适合身份证号/状态码）；VARCHAR 变长（按实际长度加 1 至 2 字节长度前缀，省空间）。VARCHAR(n) 的 n 指**字符数**不是字节数（utf8mb4 下 VARCHAR(10) 可存 10 个汉字即 40 字节）。Text 有上限：TINYTEXT 255B、TEXT 64KB、MEDIUMTEXT 16MB、LONGTEXT 4GB。

**连表查询与外键**：JOIN 类型：INNER（交集）、LEFT（左表全+右表匹配）、RIGHT、FULL（MySQL 用 UNION 模拟）、CROSS（笛卡尔积）。JOIN 原则：小表驱动大表、被驱动表关联字段必须有索引。**外键生产禁用**：外键检查加锁影响并发写、无法跨库、分库分表后失效——改应用层校验 + 定时对账。

**避免重复插入**：① UNIQUE 约束 + INSERT IGNORE（重复则忽略）② ON DUPLICATE KEY UPDATE（重复则更新）③ REPLACE INTO（先删后插，自增 id 跳变，慎用）④ 应用层查重（并发下不可靠，必须唯一索引兜底）。

**SQL 执行顺序**：FROM → ON → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。关键点：WHERE 在分组前（不能用聚合函数），HAVING 在分组后（可以用聚合函数），LIMIT 最后执行。

**IN vs EXISTS**：IN 适合子查询小表且子查询字段有索引；EXISTS 适合外层大表（逐行判断、命中即返回），对 NULL 语义更安全。

**IP 地址存储**：INT UNSIGNED（4 字节，INET_ATON/INET_NTOA 转换）优于 VARCHAR(15)：省空间、支持范围查询（IP 段）、索引更小。int(1) 与 int(10) 只是显示宽度（配合 ZEROFILL），存储范围都是 4 字节，8.0 已废弃显示宽度。

**高频追问**：

| 问题 | 答案 |
| --- | --- |
| VARCHAR(255) 与 VARCHAR(256) 区别？ | 长度前缀 1 字节变 2 字节，255 是临界值，实际影响很小 |
| 了解过前缀索引吗？ | 大字符串字段取前 N 个字符建索引，减小索引体积提高缓存命中；适用于选择性足够的前缀 |
| 哈希索引使用场景？ | 只支持等值查询，不支持范围/排序；Memory 引擎支持，InnoDB 靠自适应哈希索引加速热点页 |
| explain 发现走错索引怎么干预？ | force index 强制指定；或 analyze table 更新统计信息、调整索引设计 |
| 如何用 MySQL 实现可重入锁？ | 锁表 + UNIQUE KEY：加锁 INSERT（冲突则未获得），解锁 DELETE，配合超时清理 |

### Q15（新增 — 日志与崩溃恢复）：redo log、undo log、binlog 各自的作用是什么？两阶段提交与 double write 如何保证数据不丢失？
**A：**

**三种日志职责**：

+ **undo log**：逻辑日志，记录修改前的旧值——保证原子性（回滚）+ 提供 MVCC 历史版本链。
+ **redo log**：物理日志，记录"对哪个数据页做了什么修改"——保证持久性 + 崩溃恢复（crash-safe）。WAL 先写日志，顺序写、循环写（固定大小写满刷盘）；Buffer Pool 脏页异步批量刷盘。
+ **binlog**：Server 层归档日志（statement/row/mixed 三种格式）——主从复制 + 数据恢复。追加写，但**没有 crash-safe 能力**：它不知道哪些脏页还没刷盘，所以不能替代 redo log。

**为什么写 redo log 而不直接改 B+ 树**：redo log 是顺序写（追加），B+ 树数据页是随机写（16KB 页回写），顺序写性能高一个量级；且先改 Buffer Pool 内存页，脏页由后台批量刷盘，减少 IO 次数。

**update 语句完整执行流程**：执行器找记录（Buffer Pool 未命中则读盘）→ 更新内存数据页 → 写 undo log（旧值）→ 写 redo log（prepare）→ 写 binlog → redo log commit（两阶段提交）→ 返回客户端，脏页异步刷盘。

**两阶段提交**：redo log prepare → 写 binlog → redo log commit。崩溃恢复时以 binlog 为准：redo log 处于 prepare 且 binlog 已写 → 提交；binlog 未写 → 回滚。保证主从数据一致（避免主库有从库无 / 从库有主库无）。

**double write buffer**：数据页 16KB 大于 OS 页 4KB，刷盘断电可能"页撕裂"。double write 先把脏页顺序写入磁盘上的 double write buffer（2MB 连续区），再随机写回数据页；崩溃时用 buffer 副本修复撕裂页。8.0.20 起 redo log 记录完整页，默认不再需要 double write。

**ACID 实现机制**：原子性 = undo log 回滚；一致性 = 约束 + undo/redo 共同保证；隔离性 = 锁 + MVCC；持久性 = redo log 刷盘（innodb_flush_log_at_trx_commit=1）。

**高频追问**：

| 问题 | 答案 |
| --- | --- |
| 有了 undo log 为什么还要 redo log？ | undo 管回滚和 MVCC（逻辑层），redo 管崩溃恢复（物理层，保证已提交数据不丢），职责不同 |
| 能不能只用 binlog 不用 redo log？ | 不能：binlog 无法记录哪些脏页未刷盘，没有 crash-safe 能力 |
| redo log 在内存还是磁盘？ | 执行时在 redo log buffer（内存），事务提交时刷入磁盘 redo log 文件 |
| 事务里 SQL 太多的弊端？ | 锁持有时间长、undo/redo 膨胀、主从延迟增大，事务应短小 |

### Q16（新增 — 索引设计场景题）：WHERE a=1 AND b>2 ORDER BY c 与 WHERE a=1 AND b=2 ORDER BY c 如何建索引？a 区分度低、b 区分度高怎么办？
**A：**

**通用方法论**：等值列在前 → 范围列在后 → ORDER BY 列最后；利用索引「等值+范围+排序」天然有序免 filesort。

**场景 1：WHERE a=1 AND b>2 ORDER BY c**——索引 (a,b,c) 是错的：b 是范围条件，b>2 命中的不同 b 值下，c 在索引中不再有序，ORDER BY c 仍会 filesort。**正确方案**：(a,b) 优化过滤（b 过滤性强时）+ 小结果集 filesort 可接受；或 (a,c) 只解决排序、b 靠回表过滤（结果集大且排序要求高时）。8.0 可用降序索引配合 ORDER BY c DESC。

**场景 2：WHERE a=1 AND b=2 ORDER BY c**——推荐索引 `(a,b,c)`：a、b 都是等值条件，定位到连续区间，区间内 c 天然有序，完全避免 filesort；若 SELECT 列都在索引中则是覆盖索引。

**场景 3：a 区分度低（如性别）、b 区分度高（如订单号）**——索引 (a,b,c) 是错的：区分度低的 a 在最左列，索引退化为近似全扫描。联合索引应让区分度高的列在前：`(b,a)`（场景 2 对应 `(b,a,c)`）。代价：单独按 a 查询无法用该索引，若 a 等值查询常见需另建单列索引。

**场景 3 变体：a 区分度低（等值）+ b 区分度高（范围），如 WHERE a=1 AND b>2**——推荐索引 `(b,a)`：b>2 范围定位先大幅缩小扫描区间，a=1 通过**索引下推（ICP）****在索引层过滤（不回表）。反面教材 (a,b)：a=1 定位到近半表数据，b>2 只是在这大区间内生效——索引几乎失效，优化器甚至放弃索引走全表。修正原则：****「等值在前、范围在后」的前提是等值列区分度好**；区分度差的等值列让位给区分度高的范围列，等值条件降级为 ICP 过滤。带 ORDER BY c 时两种索引都免不了 filesort（范围列之后的排序列失效），排序代价大时另建 (a,c) 或改造查询。

**高频追问**：

| 问题 | 答案 |
| --- | --- |
| ORDER BY 一定会 filesort 吗？ | 不一定：走索引且索引顺序与 ORDER BY 同向一致时天然有序；范围条件之后的排序列失效 |
| filesort 一定慢吗？ | 结果集小（几百行）时在内存完成可忽略；大结果集落盘才慢 |
| 如何验证？ | EXPLAIN 看 Extra：Using filesort 表示有排序；key 列看实际走的索引 |

### Q17（新增 — 特殊查询索引）：按手机尾号查询（如后四位 5678）如何设置索引？
**A：**

**问题本质**：B+Tree 索引是前缀匹配——索引值从左到右比较，LIKE '%5678' 或 RIGHT(phone,4) 这类后缀匹配无法走普通索引，只能全表扫描。

**四种方案**：

| 方案 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 反向存储 | 存 REVERSE(phone) 到独立列并建索引，查询 WHERE rev LIKE REVERSE('5678')+'%' | 简单通用，5.7 及以下唯一正解 | 多一列冗余，应用层同步维护 |
| 生成列+索引 | ALTER TABLE t ADD COLUMN tail4 VARCHAR(4) GENERATED ALWAYS AS (RIGHT(phone,4)) STORED, ADD INDEX idx_tail4(tail4) | 自动维护，无冗余逻辑 | 仅 8.0+ |
| 函数索引 | CREATE INDEX idx_tail ON t((RIGHT(phone,4))) | 零额外列 | 查询函数必须与索引定义完全一致才命中 |
| Elasticsearch | 尾号维度搜索走 ES，MySQL 存全量 | 任意模糊查询 | 架构重，有同步延迟 |


**最佳实践**：8.0 用生成列+索引（直观）或函数索引（省事）；5.7 用反向存储列。尾号+状态组合查询时，联合索引 (tail4, status) 同样遵循最左前缀。
