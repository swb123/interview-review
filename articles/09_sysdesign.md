## P7 系统设计面试方法论

### 回答框架：四步推导法

```plain
① 需求澄清（2~3min）
   ├─ 功能性: 核心功能 + 扩展功能（是什么？）
   ├─ 非功能性: QPS/延迟/可用性/一致性（量化！）
   └─ 边界: 用户量/数据量/读写比/有效期

② 架构设计（5~8min）
   ├─ 画系统架构图（接入→服务→存储→中间件）
   ├─ 核心数据模型（表结构/Redis Key 设计）
   └─ 核心算法（短码生成/库存扣减/Feed 聚合）

③ 关键环节深挖（5~8min）
   ├─ 瓶颈分析（哪层最先扛不住？）
   ├─ 容量估算（公式 + 数字）
   └─ 技术选型（为什么选 A 不选 B？）

④ 优化与容灾（3~5min）
   ├─ 扩展性（水平扩容方案）
   ├─ 高可用（故障切换/降级/对账）
   └─ 成本优化（ROI 思维）
```

### P7 加分项清单

| 维度 | P6 回答 | P7 回答 |
|---|---|---|
| 容量估算 | 不估算或随口说 | 给出公式 + 具体数字 + 冗余系数 |
| 技术选型 | "用 Redis 就行" | "用 Redis Cluster 而非哨兵，因为需要 TB 级水平扩展" |
| 异常处理 | "加个重试" | "Redis 挂 → 本地缓存兜底 → Sentinel 限流 → DB 降级" |
| 数据一致性 | 只说"最终一致" | 给出对账方案 + 不一致窗口 + 业务容忍度 |
| 扩展性 | 只提水平扩展 | 给出分片数 + 扩容步骤 + 灰度切换方案 |

## 题型一：设计一个短链接系统

### 需求澄清

```plain
功能性: 长URL→短码, 短码→302重定向, 访问统计(可选)
非功能性:
  QPS: 生成 5000/s, 跳转 10万/s (读写比 1:20)
  延迟: 生成 < 50ms, 跳转 < 5ms
  可用性: 99.99%（跳转不可中断）
  短码: 7位 Base62, 不易被遍历
  存储: 100亿短链, 数据持久化, 支持过期
```

### 短码生成算法

| 方案 | 原理 | 优点 | 缺点 | P7 选择 |
|---|---|---|---|---|
| **Hash 截取** | MD5→Base62→截取7位 | 无需发号器 | 哈希冲突需兜底 | 不推荐 |
| **自增ID+Base62** | 雪花ID→转62进制 | 无冲突 | 依赖发号器 | 推荐 |
| **随机生成+去重** | 随机7位短码→查重 | 安全 | 冲突率随容量增长 | 不可预测场景 |

```java
// ID → Base62, 10亿≈6位, 62^7≈3.5万亿
public String encode(long id) {
    char[] chars = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz".toCharArray();
    StringBuilder sb = new StringBuilder();
    while (id > 0) { sb.append(chars[(int)(id % 62)]); id /= 62; }
    return sb.reverse().toString();
}
```

**防遍历**：对 ID 做加盐扰动（如 `id ^ salt` 再编码），或使用随机生成的短码。

### 架构设计

```plain
客户端 → API Gateway(限流+鉴权) → 短链服务
                                      ├─ Redis Cluster(短码→长URL, 热数据缓存)
                                      └─ MySQL 分库分表(全量存储, 按短码hash分片)
```

### 容量估算

```plain
100亿短链: DB 1.5TB(16库×32表), Redis活跃 40GB(8分片×8GB)
QPS: 跳转10万/s Redis轻松扛, 生成5000/s雪花本地+Redis写入
```

### P7 面试要点

- 主动提 302（临时重定向）vs 301（永久，浏览器缓存后不再请求后端，无法统计）
- 自定义短码：SETNX 判断冲突 + 敏感词过滤
- 短码回收：过期后不立即删除，标记 expired，定期批量清理
- 防刷：短码生成限流（同一用户/IP限制）、跳转限流

## 题型二：设计一个秒杀/抢购系统

### 需求澄清

```plain
场景: 100万人抢1万库存
峰值 QPS: 50万（抢购开始瞬间）
核心要求: 不能超卖、响应 < 100ms
```

### 全链路架构（Redis 方案）

```plain
① 前端: 按钮置灰 + 验证码 + CDN 静态化
② 网关: Sentinel 令牌桶限流(50万→5万)
③ 业务层: Hash(uid) 路由到对应 Redis 槽位
④ Redis: Lua 原子扣减(库存槽位 Slotting)
⑤ MQ: 异步创建订单 + 扣 DB 库存
⑥ DB: 订单表唯一索引防重
⑦ 对账: T+1 比对 Redis累计扣减 vs DB已售
```

### 库存槽位（Slotting）

```plain
单 Redis key DECR 极限: ~10万 QPS, 需要 50万 QPS → 至少 5 个槽位
库存: 10000 → stock:sku_0~9, 各 1000
请求按 user_id % 10 随机选槽 → 定时 MGET 汇总判断售罄
```

### 防止超卖五层保障

| 层 | 机制 |
|---|---|
| Redis Lua | `GET stock → if>0 → DECR` 原子执行 |
| Redis Hashtag | `{sku}` 确保同一商品槽位同一分片 |
| DB 唯一索引 | user\_id+sku\_id 联合唯一索引 |
| 库存字段 unsigned | 扣到负数报错 |
| 对账 | 准实时对比 Redis vs DB 差异 |

### 降级链路

```plain
正常: Redis 原子扣减 → MQ → DB
  ↓ Redis 故障
降级1: 切换纯 DB 方案(等待队列+限流)
  ↓ DB 也不可用
降级2: 返回"活动火爆，请稍后再试"
```

### 容量估算

```plain
QPS: 50万 → 网关限流到5万 → Redis 扛5万 → MQ堆积5min内消化
Redis: 10个槽位(每槽位~1万QPS) → 单分片扛, 库存走主
DB: 1万订单/秒 → 分库分表 → 异步写入
```

### 备选方案：纯 MySQL 扛秒杀流量

> **面试场景**：面试官追问"如果不用 Redis，纯 MySQL 怎么做？"

#### 核心原理

InnoDB 的**行级锁 + 原子 UPDATE** 天然保证不超卖：

```sql
-- 核心 SQL: 一条语句原子扣减
UPDATE seckill_stock
SET stock = stock - 1
WHERE sku_id = ? AND stock > 0;
-- affected rows = 1 → 扣减成功; affected rows = 0 → 已售罄
```

为什么它不会超卖？InnoDB 对 `UPDATE` 加**行级排他锁（X-Lock）**，并发 UPDATE 同一行会串行执行——`stock > 0` 的判断和 `stock - 1` 的修改在同一个锁保护范围内。

#### 架构设计

```plain
① 前端: 按钮置灰 + 验证码 + 答题（削峰）
② 网关: Sentinel 限流，只放行 5000 QPS
③ 业务层: 直接执行 UPDATE SQL
④ MySQL: 热点行排队（行锁串行化）
⑤ 异步: 扣减成功后 → MQ → 异步创建订单
```

#### MySQL 性能边界与突破方案

**瓶颈**: 单行热点商品，`UPDATE` 行锁串行 → 单行 TPS ≈ 500\~2000（取决于磁盘和网络延迟）。

**方案 1: 库存拆行（Row-level Slotting）**

```sql
-- 原来: 1 行 stock = 10000，单行 QPS 上限 ~1000
-- 改造: 10 行，每行 stock = 1000

CREATE TABLE seckill_stock_slot (
    sku_id BIGINT NOT NULL,
    slot_id INT NOT NULL,       -- 槽位 0~9
    stock INT NOT NULL,
    PRIMARY KEY (sku_id, slot_id)
);

-- 扣减时随机选槽:
UPDATE seckill_stock_slot
SET stock = stock - 1
WHERE sku_id = ? AND slot_id = FLOOR(RAND() * 10) AND stock > 0;
-- 单行 TPS 1000 × 10 槽位 = 10000 TPS
```

**方案 2: 数据库中间件分库（Sharding）**

```plain
sku_id % N → 路由到 N 个 MySQL 实例
每个实例再拆 M 个槽位行
总 TPS = N × M × 单行TPS

例如: 4 个实例 × 10 槽位 × 1000 = 40000 TPS
```

**方案 3: 应用层排队 + 令牌桶**

```java
// Guava RateLimiter 控制实际到达 MySQL 的 QPS
RateLimiter limiter = RateLimiter.create(5000);
limiter.acquire();  // 获取不到就阻塞排队
int affected = jdbc.update("UPDATE ... WHERE stock > 0");
```

#### 防止超卖 vs 防止漏卖

| 策略 | 超卖风险 | 漏卖风险 | 说明 |
|---|---|---|---|
| `UPDATE ... WHERE stock > 0` | 零超卖 | 可能漏卖 | 行锁保证串行 |
| 订单表唯一索引 | 双重保障 | — | user\_id + sku\_id 联合唯一 |
| 库存字段 UNSIGNED | 零超卖 | — | 扣到负数 MySQL 报错 |

**漏卖场景**: 用户抢到库存 → 创建订单失败（超时/校验失败）→ 库存已扣但订单没生成 → **库存少卖**。解决：异步创建订单 + 失败补偿（返还库存）。

#### Redis 方案 vs MySQL 方案对比

| 维度 | Redis 方案 | MySQL 方案 |
|---|---|---|
| **单商品 TPS 上限** | 10万（单key）/50万（Slotting） | 1000（单行）/10000（10槽位） |
| **一致性** | 最终一致（Redis→DB异步） | 强一致（SQL事务内） |
| **运维复杂度** | Redis + MQ + 对账 | 仅 MySQL（架构极简） |
| **数据可靠性** | AOF/RDB可能丢数据 | ACID保证 |
| **定位** | 高性能主方案 | Redis故障时的降级兜底 |
| **成本** | 额外Redis集群+对账 | 现有MySQL即可 |

#### P7 面试回答

> 「秒杀首选 Redis Lua + Slotting，轻松扛 10 万 QPS 以上。面试追问不用 Redis，纯 MySQL 也能做——核心是**行锁串行化 UPDATE** 保证不超卖 + **库存拆行**突破单行瓶颈。实际架构中，MySQL 方案作为 **Redis 故障时的降级兜底**，配置中心一键切换。」

```java
// 切换逻辑:
if (redisAvailable) {
    redisLuaDeduct();     // 正常链路: Redis 扛
} else {
    mysqlSlotDeduct();    // 降级链路: MySQL 扛（配合限流降 QPS）
}
```

## 题型三：设计一个社交 Feed 流

### 需求澄清

```plain
场景: 类似微博/Twitter, 用户关注后看到关注者的动态
核心问题: 推模式 vs 拉模式 vs 推拉结合
数据: 1亿用户, 人均关注200人, 日新增Feed 5000万条
```

### 推拉模式对比

| 维度 | 推模式（写扩散） | 拉模式（读聚合） | 推拉结合（P7方案） |
|---|---|---|---|
| **写操作** | 发一条Feed→写200个粉丝收件箱 | 发一条Feed→写自己发件箱 | 推给活跃粉丝 + 写发件箱 |
| **读操作** | 直接读收件箱（O(1)） | 聚合所有关注者发件箱（O(N)） | 活跃直接读 + 不活跃拉取 |
| **存储** | 大量冗余（明星1亿粉丝=1亿份拷贝） | 省存储 | 折中 |
| **延迟** | 读极快 | 读慢（需聚合） | 最优 |

### 推拉结合架构

```plain
发Feed: Feed服务 → 粉丝列表(关注图) → 活跃粉丝推写收件箱, 不活跃粉丝不推
        同时写发件箱(Redis List, 最近1000条)

读Feed: 客户端 → Feed聚合服务 → 活跃用户读收件箱 / 不活跃用户拉发件箱+聚合
```

### 存储设计

```plain
关注关系: Redis ZSet（uid → 关注者列表）
发件箱:   Redis List (uid:outbox), 最近 1000 条
收件箱:   Redis List (uid:inbox), 最近 1000 条
热数据:   Redis
冷数据:   HBase / Cassandra（时间范围查询友好）
```

### 容量估算

```plain
1亿用户, 人均关注 200, 日新增 Feed 5000万
关注关系: 1亿 × 200 = 200亿条 → ZSet约2TB
Feed存储: 1亿用户 × 2000条 × 1KB ≈ 20TB → 仅热数据在Redis
```

## 题型四：设计一个实时消息推送系统

### 需求澄清

```plain
功能: 服务端主动推送消息到客户端(APP通知/IM消息/系统告警)
延迟: < 100ms 到达
连接数: 100万并发连接
可靠性: at-least-once 送达 + 去重
```

### 连接方式对比

| 方案 | 延迟 | 带宽 | 推荐 |
|---|---|---|---|
| 短轮询 | 取决于间隔 | 高 | 不推荐 |
| 长轮询 | 中 | 中 | 兼容老设备 |
| **WebSocket** | < 10ms | 低 | 推荐 |
| MQTT | 低 | 低 | IoT 场景 |

### 架构设计

```plain
客户端(APP/Web) ←→ WebSocket ←→ 连接网关集群(Netty/NIO)
                                    ├─ 用户路由(Redis Hash)
                                    └─ 消息队列(RocketMQ) → 消息服务 + 推送服务
```

### 核心设计要点

**用户路由**：Redis Hash `user_session:{userId}` → `{gatewayId, connectId}`。消息到达时查 Redis → 找到对应网关 → 推送到该连接。

**离线消息**：用户不在线 → 消息暂存 Redis List `offline:{userId}` → 上限 1000 条 → 超限后归档 DB。

**消息去重**：消息 ID（msgId）+ 客户端本地去重缓存 → 已收到的不重复展示。

### 容量估算

```plain
100万并发连接: 单台4C8G约10万连接, 需10~15台网关
消息发送5000/s → MQ → 消费者 → 推送
```

## 题型五：设计一个配置中心

### 需求澄清

```plain
功能: 动态配置下发、版本管理、灰度发布、配置回滚
非功能:
  配置变更延迟: < 1s（长轮询/WebSocket 实时推送）
  可用性: 99.99%（即使配置中心挂了，业务仍能读取本地缓存兜底）
  容量: 10万配置项, 1000个应用
```

### 架构设计

```plain
Admin UI → Server集群(MySQL+本地缓存+Raft选主) → Client SDK(本地缓存+fallback文件)
```

### 核心设计

- **配置推送**: 客户端长轮询(30s超时) → MD5比较 → 有变更立即返回
- **灰度发布**: 配置标签（env=staging, tag=canary）→ 验证通过 → 全量
- **容灾**: Server集群 → Client本地文件缓存 → 默认值兜底（三级保障）

### 与现有方案对比

| 方案 | 优势 | 选择场景 |
|---|---|---|
| **Nacos Config** | 服务发现+配置一体 | 阿里系团队 |
| **Apollo** | 灰度发布更强、权限完善 | 需精细权限管理 |
| **自研** | 完全可控 | 有特殊需求的大厂 |

## 题型六（新增）：设计一个限流系统

### 需求

```plain
功能: 提供全局限流能力，保护下游服务
维度: 支持 QPS/并发数 限流，支持接口+用户+IP 多维
性能: 限流判断 < 1ms, 几乎不对业务 RT 产生开销
```

### 架构

```plain
业务应用(SDK本地限流) ←→ 限流服务集群(Sentinel)
                              └─ 规则存储(MySQL+Redis)
```

### 核心算法

```plain
滑动窗口: 精确控制 QPS, LeakArray环形数组, CAS无锁
令牌桶: 允许突发流量, WarmUp预热模式
漏桶: 严格平滑, 适合对外API调用
```

### P7 要点

- SDK 本地限流为主（< 1ms），远程限流为辅
- 规则变更 → 实时推送 SDK → 无需重启
- 限流中心挂了 → SDK 用本地缓存的规则继续限流（容灾）

## 题型七（新增）：设计一个分布式 ID 生成器

### 核心要求

```plain
全局唯一、趋势递增（B+Tree友好）、高性能(>10万/s)、高可用(>99.99%)
```

### 方案选型

| 方案 | 原理 | 优势 | 劣势 |
|---|---|---|---|
| **Snowflake** | 41bit时间戳+10bit机器+12bit序列号 | 本地生成，零网络开销 | 时钟回拨需处理 |
| **号段模式(Leaf)** | 从DB批量取号段，本地分配 | 无时钟依赖 | 依赖DB |
| **Redis INCR** | 单线程自增 | 简单 | 持久化可能重复 |

### 时钟回拨

```plain
回拨<5ms → 等待追上; 回拨>5ms → 自动切换备选workerId; NTP配置slew mode
单机 Snowflake: 单毫秒4096个 → ~400万 QPS
```

## 题型八（新增）：设计一个分布式任务调度系统

### 架构

```plain
Scheduler(主)──ZK选主──►Worker(多实例)
    ├─ 任务管理DB
    ├─ 时间轮+DB扫描触发
    └─ ZK分片绑定+任务执行+状态上报
```

### 核心设计

- **任务分配**: ZK临时节点绑定分片→Worker, 宕机自动迁移
- **幂等保证**: 状态机 + 业务幂等(requestId) + 分片心跳
- **故障演练**: 调度中心挂→毫秒级选主恢复; Worker挂→分片迁移重试
